# Аудит расчётной логики вне Щита — для будущего единого расчёта по проекту

Цель документа: собрать в одном месте ВСЮ существующую логику расчёта работ, расходников,
кабеля и штроб, разбросанную сейчас по нескольким независимым модулям (Пул, Проект квартиры,
Расходники, генератор работ, учёт инструмента). Щит (Конфигуратор щита) сюда намеренно НЕ
включён — у него отдельная, самодостаточная логика (`shield-configurator-v28.js` и соседние
`shield-*`/`manual-scheme-v28.js` файлы).

Практическая цель на будущее: когда в «Проект квартиры» (или в новом едином модуле) будет
собираться ПОЛНЫЙ расчёт по объекту, этот документ — чек-лист, что именно уже посчитано
где-то в приложении и с какими формулами/нормами, чтобы не терять и не дублировать логику
при объединении.

## 1. Карта источников (кто что считает сейчас)

Пять независимых мест, где сегодня появляются позиции работ/материалов (кроме щита):

| Источник | Файл | Что считает | Куда падает |
|---|---|---|---|
| Пул розеток/штроб | `assets/js/modules/pool/pool-engine-v29.js` (движок) + `pool-v29.js` (UI) | Штробы, подрозетники, распайки, коннекторы, кабель — **приближённо по комнатам** (блоки постов) | `EP.Collector.pushPool()` → предварительная смета |
| Проект квартиры → Расчёт | `assets/js/modules/plan/plan-calc.js` | То же самое, но **точно по построенным трассам** (реальный чертёж); приоритет над Пулом, если трассы построены | `EP.Plan.Calc.estimateItems()` → `EP.Collector.pushPlan()` |
| Логика расходников (кабель/штробы) | `assets/js/modules/consumables/cable-consum.js` (движок) + `consumables-ui.js` (экран «Расходники») | Крепёж кабеля (гвозди/выстрелы/площадки/стяжки/гофра/лента), инструмент (коронки/диски с ресурсом по материалам), мешки мусора/пылесоса | В предварительную смету вручную кнопками экрана |
| Калькулятор «мелочёвки» | `assets/js/modules/estimate/consumables.js` (экран «Затраты»/consumables) | Нормированная мелочёвка (клеммы, гофра, дюбель-хомут, гипс, ПУГВ, НШВИ, маркировка, изолента, термоусадка) — по параметрам объекта (точки/метры кабеля/коробки/модули) | `d.setSourceItems("consumables", …)` |
| Генератор работ из материалов | `assets/js/modules/estimate/pick-and-estimate.js` (`genWorksFromDraft`) | Подбирает РАБОТЫ из активной БД под уже добавленные МАТЕРИАЛЫ по regex-правилам | `d.setSourceItems("autowork", …)` |

Всё сходится в `EP.EstimateDraft` (предварительная смета) через **именованные источники**
(`setSourceItems(sourceId, items)` — повторный вызов с тем же `sourceId` заменяет предыдущий
вклад этого источника, без дублей). Дальше пользователь переносит предварительную смету в
основную (`EP.Estimate`, кнопка «В основную»).

Общий формат позиции везде одинаковый: `{ type: "material"|"work", name, qty, unit, price }`.

## 2. Пул розеток/штроб — `EP.PoolEngine` (pool-engine-v29.js)

Приближённый расчёт **по блокам** (пользователь описывает набор точек на комнату/зону, а не
рисует чертёж). Вход — массив `blocks`, каждый блок: `{ material, route, height, sockets, sw1,
sw2, sw3, pass, passKeys, cross, crossKeys, tv, internet, warmFloor, dedicated }`.

### 2.1 Дефолты (`DEFAULTS`)

```
ceilingHeight: 270 см
mode: "junction" ("junction"=в распайках | "boxes"=в подрозетниках)
shape: "round" (кабель "round"|"flat")
crown: 68 мм (Ø коронки подрозетника)
depth: { std: 45, deep: 65 } мм (глубина подрозетника)
sizeRegular: "25x30" (обычная штроба)
sizeWarm: "50x50" (штроба тёплого пола)
lvSize: "25x30" (штроба слаботочки)
socketGauge: "2.5" мм² (розетки), lightGauge: "1.5" мм² (свет)
connectorMode: "gml" ("wago"|"gml"|"siz")
dropsPerSocketJunction: 2, dropsPerSwitchJunction: 2 (спусков на 1 распайку)
shrinkCmPerJoint: 5 см термоусадки на стык, heatShrinkType: "12/4"
```

**Ёмкость штробы** (`capacity`, сколько кабелей влезает по размеру×форма×сечение):
```
25x30: round { 2.5мм²: 2, 1.5мм²: 3 }, flat { 2.5мм²: 3, 1.5мм²: 4 }
30x30: round { 2.5мм²: 3, 1.5мм²: 4 }, flat { 2.5мм²: 4, 1.5мм²: 5 }
```

**Шаблоны соединений на механизм** (`templates` — сколько pin-контактов даёт механизм):
```
switch_1: pin2×4          pass_1: pin2×6         cross_1: pin2×9
switch_2: pin2×3, pin4×2  pass_2: pin2×8, pin4×1 cross_2: pin2×15, pin3×1
switch_3: pin2×4, pin4×2
```
(pass/cross = проходной/перекрёстный выключатель; максимум 2-клавишный шаблон — для
3-клавишного проходного/перекрёстного шаблона в движке нет, берётся `_2` как верхняя граница.)

### 2.2 Формулы

**Кабели по блоку** (`cablesOfBlock`):
- выключатели: 1-2 клавиши = 1 кабель, 3 клавиши = 2 кабеля (`swCables`)
- проходной/перекрёстный = 2 кабеля × число клавиш (`passCables`/`crossCables`)
- розетки: 1 кабель на блок розеток / отдельную линию (`socketCables`), если есть хоть одна розетка или `dedicated`
- слаботочка: `tv + internet` (каждый — отдельный кабель)

**Подрозетники по глубине** (`podrozOfBlock`):
- глубокие (65мм): выключатели + проходные + перекрёстные + тёплый пол
- обычные (45мм) — режим "boxes": розетки туда же; ТВ/интернет/`dedicated` — всегда обычные

**Штробы** (силовые, в `calc()`):
- маршрут "ceiling" (с потолка): весь силовой поток идёт короб→потолок
- маршрут "floor" (с пола): пол→короб несёт ВСЁ (розетки+свет), короб→потолок — только свет
- слаботочка — отдельная штроба (`lvSize`), 1 на блок
- тёплый пол: короб→пол всегда `50×50`; если маршрут потолочный — доп. `25×30` короб→потолок на подачу
- количество штроб = `ceil(кол-во_кабелей / ёмкость_штробы(размер, форма, сечение))`

**Кабель по метражу**: розеточный/световой считается как штробы (маршрут×высота), в режиме
"boxes" силовые кабели удваиваются (`×2`, т.к. заходят в подрозетник и обратно).

**Распайки** (только режим "junction"): 1 распайка на блок розеток (1-5 розеток на распайку),
1 распайка на КАЖДЫЙ выключатель/проходной/перекрёстный.

**Коннекторы** (`connectors()`) — perенос логики со старого пула:
- распайки: суммарные "спуски" (drops) делятся по `dropsPerSocketJunction`/`dropsPerSwitchJunction`
  на коробки, каждая коробка даёт `pin(2+N)` контактов ×3 (L/N/PE)
- выключатели/проходные/перекрёстные — по шаблонам `templates` (см. 2.1)
- режим `connectorMode`: `wago` → материалы `pinN` (ВАГО N-пин), `siz` → `sizN`, `gml` (по
  умолчанию) → гильзы по `sleeveByWires(w)`: ≤4пр→gml4, ≤6→gml6, ≤8→gml8, иначе gml10
- термоусадка (только gml/siz): `Σ_соединений × shrinkCmPerJoint / 100` метров

### 2.3 Позиции черновика (`buildDraftItems`)

- `work`: «Штробление {размер} {материал строчными}», м
- `work`: «Высверливание подрозетников обычных/глубоких {материал}», шт
- `material`: «Подрозетник Ø{crown} 40-50 мм / 65 мм глубокий», шт
- `material`: «Распаечная коробка (потолок)», шт (сумма распаек)
- `material`: коннекторы (ВАГО N-пин / ГМЛ N / СИЗ на N проводов), шт
- `material`: «Термоусадка {heatShrinkType}», м
- Кабель НЕ кладётся в черновик Пула — только в `result.cable` (используется потребителями отдельно)

## 3. Проект квартиры → точный расчёт по трассам — `EP.Plan.Calc` (plan-calc.js)

Тот же смысл, что и Пул, но данные берутся из РЕАЛЬНОГО чертежа (`p.routes`, построенных
автотрассировкой `EP.Plan.Routes`) — точнее приближённого расчёта по комнатам. Если трассы не
построены — используется fallback на `EP.PoolEngine.calc()` через `buildBlocks(p)`/`runEngine()`
(агрегирует точки по комнатам, медианная высота розеток, эвристика материала стены комнаты).

### 3.1 `calcByRoutes(p)` — точный расчёт (приоритетный путь)

**Штробы-спуски** (`addStrobe`, по каждой точке с построенной трассой):
- материал берётся с КОНКРЕТНОЙ стены точки (`G.wallMatOf`), не общий по комнате
- высота спуска — `RT.pointVert(p, el)` (до короба/потолка/пола по фактической геометрии)
- три НЕЗАВИСИМЫЕ строки по виду (не смешиваются даже при одинаковом физическом размере):
  - **power** — обычный размер (`s.chaseW×s.chaseH`, дефолт 25×30мм), количество штроб =
    `ceil((inCnt+outCnt) / ёмкость)` — ёмкость берётся из `EP.PoolEngine.DEFAULTS.capacity`
  - **lv** (слаботочка: `layer` = lv/tv/cctv) — суффикс «(слаботочка)» в названии, своя строка
  - **warm** (тёплый пол) — `s.tpChaseW×s.tpChaseH` (дефолт 50×50), ТОЛЬКО от термостата вниз в пол;
    подача к самому термостату — обычная штроба (power)
- у щита: отдельный спуск по количеству приходящих линий (`RT.panelVert(p)`), силовые и
  слаботочные линии в щит — тоже РАЗНЫМИ строками

**Подрозетники** (по материалу СВОЕЙ стены точки):
- глубокие: `switch`, `warmfloor`
- обычные: `socket`, `tv`, `internet`, `ac`, `sensor`
- `junction` (распаечная коробка) — считается отдельно, НЕ как подрозетник

**Кабель по маркам** (не по сечению, а по конкретной марке провода):
- марка берётся из `p.circuits[].cable`, если линия привязана к автомату (задаётся в щите/схеме)
- иначе по слою: `light` → «ВВГнг(А)-LS 3×1.5», `warm` → «Кабель тёплого пола», lv-слои →
  «Слаботочный (UTP/RG-6)», всё остальное (по умолчанию, розетки) → «ВВГнг(А)-LS 3×2.5»
- длина = длина полилинии трассы + вертикальный спуск точки (× `hopVertMul`, см. ниже) + спуск у щита
- запас: `settings.cableReserve` % (дефолт 10%), применяется на итоговый метраж по марке

**`hopVertMul(p, route)`** (в `plan-routes.js`, используется здесь) — если на конце хопа НЕТ
распайки/щита, штроба у этой точки проходится дважды (вниз к посту и обратно вверх продолжать
шлейф) → кабеля нужно вдвое больше на этом участке (сама штроба физически одна, только метраж
кабеля разный).

**Проходки через стены** (гильзы Ø `settings.sleeveD`, дефолт 20мм): группировка по месту
(округление координаты до 20см — общая стена двух комнат считается одним местом), максимум 2
кабеля на гильзу (`ceil(n/2)`), группировка по материалу стены.

**Ниша под щит** (как в конфигураторе щита): вырубка = число модулей корпуса (`neededModules()`
из `EP.Plan.Scheme`, либо явно заданный `s.panelBox.modules`) × «работа: Вырубка ниши под щит
{материал}», + фикс. позиция «Монтаж щита в нишу/стену» × 1.

**Коннекторы** (`connectorsByRoutes`) — та же логика шаблонов, что в Пуле (см. 2.2), НО:
- распайки: pin-count = **точное** число сходящихся кабелей из графа трасс (`inCnt[id]+outCnt[id]`),
  не оценка — точнее, чем в Пуле
- выключатели: шаблон берётся по РЕАЛЬНОМУ виду поста (`el.swKind` normal/pass/cross, `el.keys`
  1-3) через `switchTemplateKey()`, а не усреднённо
- посты «switch» ВНУТРИ блока (группового элемента) считаются простым 1-клавишным (блок не хранит
  клавишность внутри себя)

### 3.2 Приближённый путь (`runEngine`, fallback без построенных трасс)

`buildBlocks(p)` агрегирует все НЕ-existing (не «уже существует») элементы по комнатам через
`roomStats()`: считает `sockets/sw/light/tv/internet/warm/ac`, медианную высоту розеток
(`socketHeights` по факту расставленных точек, а не фиксированный дефолт), материал = `room.material
|| settings.wallMaterial`. Каждая комната → один «блок» для `EP.PoolEngine.calc()` (клавишность
выключателей теряется — блок описывается как `sw1 = общее число выключателей`, без разбивки на
клавиши/проходной/перекрёстный — это ГРУБЕЕ, чем `calcByRoutes`).

### 3.3 Цены

`priceFor(name, type)` — поиск в `EP.Database.getItemsByType(type)`: точное совпадение по имени
(без учёта регистра), иначе двунаправленная подстрока (имя товара входит в имя позиции ИЛИ
наоборот). Позиции без совпадения помечаются «нет цены в БД» и не входят в сумму.

## 5. Логика расходников по кабелю/штробам — `EP.CableConsum` (cable-consum.js)

Отдельный, полностью настраиваемый пользователем движок «мелочёвки для монтажа» — крепёж кабеля
и расходники инструмента. Хранится в `localStorage` (`ep_cable_consum_logic_v29`), все нормы
редактируются на экране «Логика расходников». Вход — метраж кабеля/штробы, число точек/коробок,
материал(ы), «мокрый рез» (да/нет).

### 5.1 Дефолтные нормы (`DEFAULTS`)

**Крепёж поверхностного кабеля** (кабель минус штроба — в штробе крепёж не нужен):
- прямой монтаж по потолку: `3` площадки/м, `3` стяжки/м, `3` (гвоздь+выстрел)/м
- гофра по потолку: `3` клипсы/м, каждая клипса = 1 гвоздь + 1 выстрел
- по полу (всегда гофра ПНД): лента `0.6` м/м кабеля (рулон 20м), `4` (гвоздь+выстрел)/м
- распайка: `4` гвоздя + `4` выстрела на коробку

**Упаковки** (округление вверх с допуском): гвозди — пачка 1000 (допуск 200), выстрелы — баллон
на ≈1000 (допуск 200), стяжки — уп. 100, площадки — уп. 100.

**Инструмент** (`tools[]`, ресурс по материалу — отверстий/метров на инструмент до замены):
| id | вид | размер | функция | Бетон | Кирпич | Панель | Мягкий |
|---|---|---|---|---|---|---|---|
| t76 | коронка | 76мм | подрозетники | 15 | 40 | 12 | 120 |
| t82 | коронка | 82мм | подрозетники в подрозетниках (boxes) | 12 | 30 | 10 | 90 |
| t52 | коронка | 52мм | иное | 20 | 50 | 16 | 150 |
| d125 | диск | 125мм (штроба small) | штроба | 60 | 120 | 50 | 300 |
| d150 | диск | 150мм (штроба big) | штроба | 50 | 100 | 40 | 250 |

`wetFactor: 1.5` — при резе с водой ресурс инструмента умножается на 1.5 (меньше расход на
отверстие/метр). Диски всегда парой (`discs.pair: 2`).

**Мешки мусора/пылесоса** (`trashBags`/`vacBags`): твёрдые материалы (Бетон/Кирпич/Панель) —
1 мешок на 10м штробы ИЛИ 30 подрозетников; мягкие (газоблок и т.п.) — 1 на 20м / 50 шт;
пылесос — отдельная норма (30м штробы / 40 подрозетников на мешок, без разделения тв/мягкий).

**Буры**: 6мм × 2шт, 8мм × 3шт — фиксированно, если есть хоть один подрозетник или коробка.
**Пика**: 1шт, **карандаш**: 1шт — если есть подрозетники или штроба.

### 5.2 Три независимых режима расчёта (`calc(inp)`, `mode`)

- `mount` — крепёж (гвозди/баллон/площадки/стяжки/гофра/лента) + буры/пика/карандаш +
  «объектный» инструмент по счётчикам (ниша щита/бризер/канализация/«иное» — своя функция на
  инструмент, задаётся пользователем в редакторе инструментов этого экрана)
- `materials` — коронки/диски/мешки, АГРЕГАЦИЯ ДО округления (несколько строк материалов дают
  дробный расход инструмента, округляется один раз в конце, чтобы не переокруглять по каждому
  материалу отдельно); хранит `wear` (доля использования последней единицы) для UI
- `single` — оба режима сразу (дефолт для одиночного расчёта без разбивки по материалам)

## 6. Калькулятор «мелочёвки» по нормам — estimate/consumables.js

Простая линейная модель «норма × параметр объекта × (1+запас%)», независимая от §5 (перекрытие
нужно гасить самому пользователю — «отключи то, что уже считает пул или щит, чтобы не задвоить»).

**Параметры объекта** (`autoParams()` — эвристика по regex ИЗ УЖЕ добавленной сметы, правится
руками):
- `points` — по имени «подрозетник» ИЛИ «розетка|выключатель|светильник|датчик»
- `cableM` — по позициям с ед. «м» и именем «кабель|ввг|nym|пвс|сип|провод»
- `boxes` — по имени «коробка|распайка|распаечн»
- `modules` — по имени «автомат|диф|узо»

**Нормы по умолчанию** (`DEFAULT_NORMS`, `per`: points/cableM/boxes/modules/project):
```
Клеммы Wago            2 шт / точку        (вкл)
Гофра / труба          0.5 м / точку       (выкл — обычно уже в пуле)
Подрозетник            1 шт / точку        (выкл — обычно уже в пуле)
Дюбель-хомут/клипса    2 шт / метр кабеля  (вкл)
Стяжка кабельная       1 шт / метр кабеля  (вкл)
Клеммы Wago            5 шт / коробку      (выкл)
Гипс/алебастр          0.1 кг / коробку    (вкл)
Провод ПУГВ            0.3 м / модуль щита (вкл)
Наконечник НШВИ        2 шт / модуль щита  (вкл)
Маркировка             1 шт / модуль щита  (вкл)
Изолента               2 шт / объект       (вкл)
Термоусадка            1 уп / объект       (вкл)
```
Округление: `шт`/`уп` → вверх (`Math.ceil`), остальное → до 0.01.

## 7. Генератор работ из материалов — pick-and-estimate.js (`WORK_RULES`)

Кнопка «Добавить работы по материалам» на главном экране: по уже добавленным МАТЕРИАЛАМ в
предварительной смете подбирает соответствующие РАБОТЫ из активной БД (regex по названию,
никакого жёсткого id-маппинга — работает на любой пользовательской базе).

Правила сопоставления материал→работа (`matchMat` — что считается материалом этого вида,
`workKw` — по какому regex искать работу в БД, `prefer`/`cable` — доп. приоритет выбора при
нескольких найденных работах):

| Материал (regex) | Работа ищется по | Приоритет/особый разбор |
|---|---|---|
| кабель/провод (ввг, nym, пвс, кввг, сип, пунп, пугв, пв-N, шввп) | «укладка/прокладка/монтаж/затяжка/прокидка кабеля» ИЛИ «кабель+штроба/гофра/лоток/труба/канал» | по сечению кабеля (`≤4мм²`/`≤10мм²`/`>10мм²`) выбирается более подходящая работа `pickCableWork` |
| подрозетник / установочная коробка | «подрозетник/установочная коробка» | предпочтение «монтаж/установка/высверливание/сверление» |
| распайка / распредкоробка | «распайка/распредкоробка» | предпочтение «монтаж/установка/расключение» |
| механизм (розетка/выключатель/диммер/кнопка/термостат — НЕ подрозетник/автомат/узо) | «внутренняя точка» ИЛИ «установка/монтаж/подключение {розетка|выключатель|механизм|диммер|термо}» | если есть универсальная «внутренняя точка» — берётся она; иначе — под конкретный подтип механизма |

Демонтажные работы (`демонтаж|снят|удален|разбор`) исключаются из кандидатов всегда.
Материалы без совпадающего правила ИЛИ без найденной работы в БД — пропускаются, с логом
«Работы не найдены в базе: …» (не блокирует остальные).

## 8. Нормы выработки (часы) для инструмента — tools.js (`NORMS`)

Используются для прикидки часов работы ресурсного инструмента (режим "hours") из уже
рассчитанной сметы — единственное место в приложении, где есть «скорость работы в час»:

```
Штробление                                    10 м/ч
Высверливание подрозетников / коронка          8 шт/ч
Укладка/прокладка кабеля, затяжка             30 м/ч
Монтаж коробок/подрозетников, установочных     12 шт/ч
Внутренняя точка, подключение розетки/выкл.    6 шт/ч
(остальные работы, не попавшие в правила)      8 (DEF_NORM, дефолт)
```
«Уборка» (для расхода пылесоса по часам) считает только пыльные работы: штроба/высверливание
подрозетников/коронка/алмазное/сверление.

## 9. Каталог материалов/работ — `EP.Database` (database-core.js)

Единая модель позиции для ВСЕХ разделов приложения (материалы и работы — одна и та же схема,
различаются только `type`):
```
{ id, type: "material"|"work", name, category, subcategory, unit, price: Number,
  currency, active: Boolean, deleted: Boolean }
```
Две независимые базы: `"my"` (моя) и `"server"` (сервера) — не смешиваются, вся выборка идёт
из ОДНОЙ активной базы (`getActiveDb()`); есть копирование позиций server→my с дедупом по
`type+category+subcategory+name`. Импорт понимает несколько форматов (`items`, `workDB`/`matDB`
раздельно, CSV с колонками name/type/category/subcategory/unit/price, объект `{Категория: [...]}`).

## 10. Сборщик предварительной сметы — `EP.Collector` (collector-bridge.js)

Единая точка входа «В смету» для Пула/Плана/Щита (щит — своя логика, см. верх документа).
`aggregate(arr)` — общая логика схлопывания одинаковых позиций (ключ `type|нормализованное_имя|
unit`, количества суммируются, цена берётся у первой непустой записи, иначе — `priceByName()`
ищет по каталогу лучшим совпадением: точное имя = score 100, взаимная подстрока = score 60).

`setSourceItems(sourceId, items)` в `EP.EstimateDraft` — источники: `"pool"`, `"plan"`,
`"shield"`, `"consumables"`, `"autowork"` — каждый переписывает СВОЙ прошлый вклад целиком при
повторном вызове, без дублей между вызовами одного источника (но источники между собой НЕ
дедуплицируются автоматически — например, кабель может быть добавлен и Планом, и Расходниками
одновременно, если пользователь явно нажал обе кнопки).

## 11. Дубли и нестыковки — на заметку при объединении в один расчёт

- **Пул vs Проект квартиры** — два независимых источника правды с почти одинаковой логикой
  штроб/подрозетников/распаек/коннекторов (одни и те же формулы буквально скопированы между
  `pool-engine-v29.js` и `plan-calc.js`, а не переиспользуются как общий модуль). План точнее
  (реальный чертёж), Пул — единственный вариант для проектов БЕЗ построенного плана.
- **Мощность в ваттах нигде не считается** — ни один из модулей не хранит поле «Вт» на точке;
  весь расчёт кабеля/автоматов идёт от факта количества точек и номинала автомата (щит), не от
  реальной электрической нагрузки.
- **Расходники (§5) вшиты в точный счёт по трассам** (`plan-calc.js` → `addConsumItems()`,
  вызывается из `calcByRoutes()`) — крепёж/буры/коронки/диски/мешки теперь считаются
  автоматически по уже посчитанным метрам штробы/подрозетникам/коробкам/кабелю, тем же
  движком `EP.CableConsum`, без ручного захода на экран «Расходники» (см. CLAUDE.md,
  инвариант «Расходники по кабелю/штробам»). **Мелочёвка (§6)** в это НЕ включена — остаётся
  отдельным ручным/редактируемым калькулятором, пересечение по смыслу (клеммы/гофра) с §5
  по-прежнему гасится только текстовой подсказкой «отключи то, что уже считает пул/план».
- **Генератор работ (§7)** и «точный счёт по трассам» (§3) оба производят строки `work`, но
  РАЗНЫМИ путями: §3 сразу пишет и работу, и материал по своей формуле; §7 донабирает недостающие
  работы под материалы, которые попали в смету БЕЗ автоматически подобранной работы (например,
  добавленные вручную из «Материалы»). При использовании обоих сразу возможен задвоенный «work:
  Штробление …», если пользователь сначала взял точный счёт (уже содержит `work`), а потом ещё
  нажал «Добавить работы по материалам» поверх.
- **Нормы выработки (§8)** существуют ТОЛЬКО для расхода инструмента (часы работы), не
  используются больше нигде — например, не влияют на смету по срокам/трудозатратам для клиента
  (такой раздел — «смета по работам» — в бэклоге CLAUDE.md ещё не сделан).
- **Ниша щита** считается идентично в двух местах: `plan-calc.js` (§3.1, если план собран) и
  внутри самого конфигуратора щита (вне области этого документа) — при объединении логично
  оставить один источник правды.
