**Главный вывод:** в репозитории одновременно живут **два поколения системы доступа** — легаси (`auth.js`, `admin.js`, `access-guard.js`, `existing-firebase-access.js` со схемой `status`/`isApproved`/`blocked`) и новый «V29 Secure Access» (`functions/index.js` + `access-policy.js` + `firestore.rules` со схемой `role`/`accessStatus`/`subscription.plan`). Они несовместимы, и от того, какие правила реально развёрнуты в Firebase, зависит, что именно сломано: либо регистрация и админка не работают, либо открыта критическая дыра эскалации привилегий.

## 1. Безопасность

### 🔴 Критично

**S1. Клиент пишет в `users/{uid}` напрямую, а правила это запрещают — либо всё сломано, либо всё открыто.**
- `firestore.rules:26` — `allow create, update, delete: if false` для `users/{uid}`.
- Но `auth.js:113` (регистрация мастера), `auth.js:134` (самовыдача триала на 10 дней), `auth.js:138` (lastLoginAt), `admin.js:317` `writeUserDoc()` (одобрить/заблокировать/назначить админом/баланс) — все пишут в `users` из браузера.
- Если в проде развёрнуты правила из репозитория → **регистрация мастеров, триал и половина админки не работают** (permission-denied).
- Если в проде развёрнуты старые, более мягкие правила (при которых этот код работает) → **любой пользователь через консоль браузера может записать себе `role: "admin"`, `status: "approved"`, продлить триал** — критическая эскалация привилегий.
- Правильная модель уже есть в репо: запись через Cloud Functions (`ensureUserProfile`, `adminSetUserAccess`). Клиент нужно перевести на неё.

**S2. Админка вызывает 6 Cloud Functions, которых не существует.**
`admin.js` вызывает `grantSubscription`, `cancelSubscription`, `setAiAccessMode`, `topUpAiBalance`, `setAiBalanceExact`, `setUserSecurityPolicy` (`admin.js:219-221, 366, 373-378`). В `functions/index.js` есть только `ensureUserProfile`, `getAccessPolicy`, `adminListUsers`, `adminSetUserAccess`. Выдача/отмена подписки, режим ИИ и пополнение баланса из админки **не работают вообще**. Существующая `adminSetUserAccess` из UI не вызывается ни разу.

**S3. Админка читает коллекции, запрещённые правилами.**
`user_subscriptions`, `ai_accounts`, `ai_payment_requests`, `subscription_payment_requests` (`admin.js:38, 290, 328`) не описаны в `firestore.rules` → попадают в catch-all `allow read, write: if false`. Вкладка «Запросы» и данные подписок в карточке пользователя мертвы.

**S4. Подпись доступа `accessSignature` — театр безопасности.**
HMAC вычисляется и сохраняется (`functions/index.js:157, 227`), но **нигде не проверяется** — ни на клиенте, ни в функциях. При не заданном `ACCESS_SIGNING_SECRET` пишется строка `"server-secret-not-configured"` и всё продолжает работать. Либо добавить проверку в `getAccessPolicy`, либо удалить механизм.

**S5. В репозитории нет `firebase.json` и `.firebaserc`.**
`firestore.rules` и `functions/` невозможно задеплоить из репо — нет конфигурации деплоя. Это прямой источник расхождения «код в репо ≠ правила в проде» (см. S1).

### 🟠 Высокий риск

**S6. Контроль подписки — только на клиенте.**
`access-guard.js` выкидывает на логин при истёкшей подписке, `access-policy.js.can(feature)` прячет кнопки — всё это обходится через devtools за минуту. Firestore-правила не проверяют подписку: заблокированный/просроченный пользователь сохраняет полный доступ к своим данным `user_db`, `drafts`, `estimates` и чтению `server_db`. Если платный доступ должен реально закрываться — это надо дублировать в правилах (например, `accessStatus == "approved"` для чтения `server_db`).

**S7. API-ключи OpenAI/Gemini хранятся в localStorage открытым текстом и уходят в API прямо из браузера** (`ai.js:14, 58`, `admin.js:107-110`). Любая XSS = кража ключей. «Серверный» ключ сейчас тоже лежит в localStorage устройства админа; план «вынесем ключи в Firestore + прокси» (`admin.js:122`) в текущей модели правил означал бы раздачу ключа всем — делать только через Cloud Functions-прокси, ключ держать в секретах функций.

**S8. Нет Content-Security-Policy и SRI.**
`index.html` не задаёт CSP (meta или заголовок хостинга), внешние скрипты gstatic подключены без `integrity`. Для приложения, целиком построенного на innerHTML-рендеринге, CSP — главный страховочный трос.

**S9. Email владельца захардкожен в 4 местах** (`firestore.rules:13`, `functions/index.js:9`, `auth.js:4`, `admin.js:9`). Смена владельца или компрометация почты Google = смена всех точек. Лучше custom claims (`admin: true`) через Admin SDK.

### 🟡 Средний риск

- **S10.** `esc()` в ~8 модулях не экранирует одинарную кавычку (`ai.js:60`, `stock.js:14`, `documents.js:11`, `profile.js:63`…). Пока все атрибуты в двойных кавычках — не эксплуатируется, но одна правка на `'` — и появится XSS. Вынести один правильный `esc` в общий модуль.
- **S11.** `nav-header.js:8` `clean()` просто удаляет `&<>` вместо экранирования; заголовок берётся из textContent страницы — риск низкий, но паттерн неверный.
- **S12.** Правила не ограничивают размер/структуру документов в `user_db`, `drafts`, `estimates` — пользователь может писать мегабайтные документы произвольной формы (расходы, DoS-вектор по счёту).
- **S13.** `visual-firebase-sync.js:75` подменяет `localStorage.setItem` глобально (monkey-patch) — хрупко и мешает отладке.
- **S14.** `isAdmin()` в правилах делает `exists()` + `get()` на каждую проверку — двойные тарифицируемые чтения на каждый запрос админа.

### ✅ Что сделано хорошо

- Default-deny в конце правил, изоляция данных по `uid`, `admin_logs`/`security_events` защищены от записи с клиента.
- Экранирование HTML присутствует в подавляющем большинстве UI-модулей (admin, clients, database, stock, documents, tools…).
- Роутер — белый список маршрутов, hash не попадает в HTML; `eval`/`new Function` не используются.
- Cloud Functions аккуратно проверяют аутентификацию и роль (`assertSignedIn`/`assertAdmin`), ведут `admin_logs`.
- Firebase web-config в репо — это нормально (он публичный по дизайну), безопасность держится на правилах.

## 2. Архитектура и качество кода

**A1. Два поколения кода сосуществуют.** Легаси-контур (auth.js + admin.js + access-guard.js + existing-firebase-access.js, 824 строки) и новый V29 Secure Access (functions + access-policy.js). Две схемы профиля пользователя конкурируют: `status/isApproved/blocked/subscriptionPlan/trialEndsAt` против `role/accessStatus/subscription.{plan,active,expiresAt}`. Это причина большинства проблем из раздела 1. Нужно выбрать V29-схему и выпилить легаси.

**A2. Мёртвый код ~115 КБ:**
- `assets/js/modules/pool/pool-v22-clean-monolith.js` — 91 КБ, отключён в `index.html:76`, помечен «удалить файл позже»;
- `assets/js/modules/shield/shield-configurator-v28.css` — 24 КБ, не подключён нигде (стили щита живут в `assets/css/shield.css`).

**A3. 50+ `<script>` тегов без сборщика,** порядок загрузки критичен, версии `?v=NNNN` проставляются вручную и уже разъехались (от 2918 до 3024). Минимум — генерировать версию из `version.json` одним местом; лучше — Vite/esbuild.

**A4. Дублирование хелперов:** `esc()`, `num()`, `tsDate()`, `money()` скопированы в ~15 модулей с расхождениями (см. S10). Нужен один `assets/js/core/utils.js`.

**A5. Нет тестов, линтера и CI.** Ни одного теста в репо; для «защищённых зон» (БД, конфигуратор щита) хотя бы смоук-тесты расчётов сильно снизили бы риск регрессий.

**A6. docs/ — 54 файла чейнджлогов/чеклистов** — история полезна, но актуальную инструкцию (как деплоить rules/functions, какие коллекции существуют) собрать в один README.

## 3. Визуализация / UI / UX

### ✅ Сильные стороны

- **Развитая система тем** (`visual-settings.js`): 24 темы с пресетами эффектов, режимы день/ночь, стекло/блюр, регулировка радиусов, плотности, масштаба текста, звук и хаптика, perf-режимы `auto/lite/rich` с «обучением» уровня производительности.
- **Облачная синхронизация визуала** (`visual-firebase-sync.js`) в разрешённый путь `user_db/{uid}/settings/visual` с разумной политикой «локальное главнее, пустое облако не затирает».
- Тёмная/дневная схема через `body[data-visual-mode]`, CSS-переменные, адаптивные `@media` в базовых стилях; единая шапка навигации (`nav-header.js`).

### ⚠️ Проблемы

**V1. Доступность почти отсутствует.** На 23 страницы — один `aria-*` атрибут (admin.html), `alt` нет ни одного, интерактивные элементы админки — кнопки без подписей («✎», «✕», «➕» только с title). Скринридер по приложению не пройдёт.

**V2. Системные настройки ОС игнорируются:** нет ни одного `prefers-reduced-motion` / `prefers-color-scheme` в CSS. Собственный тумблер `reduceMotion` есть — но пользователь с вестибулярными нарушениями получит анимации до того, как найдёт настройку. Добавить `@media (prefers-reduced-motion: reduce)` глобально.

**V3. 74 `!important` в одном только `base.css`** (в основном day-mode оверрайды `base.css:527-539`) — каскад хрупкий, любая новая тема будет воевать с ним. Правильнее — переменные на `body[data-visual-mode="day"]` вместо точечных перекрасок.

**V4. Инлайновые стили в JS-шаблонах админки** (`admin.js:263, 302-306` — `style="flex:1;min-width:140px"`) — вынести в admin-console.css.

**V5. Стекло + прозрачность карточек (opacity 0.58-0.72) поверх живых фонов** — на части тем контраст текста на просвечивающем фоне может падать ниже WCAG AA; стоит прогнать основные темы через проверку контраста, особенно muted-тексты.

**V6. `prompt()`/`confirm()`/`alert()` в админке и ИИ** (`admin.js:277-280`, `ai.js:179, 210`) выбиваются из дизайн-системы — заменить на модалку, которая уже есть (`#ep-admin-modal`).
