# Electric Pro V29 — правила работы для Claude

PWA для электриков (RU). Vanilla JS (ES2020), IIFE-модули в `window.EP.*`, БЕЗ сборки,
БЕЗ TypeScript/React — не переписывать. Firebase Hosting/Auth/Firestore. Деплой:
push в `main` → GitHub Actions (`firebase-deploy.yml`) → синтакс-чек + `node test/run.js`
(гейт) → Firebase. APK-путь: PWA + TWA/Capacitor (см. docs/APK.md).

## Процесс (выработан с пользователем)
- Общение по-русски. НИКОГДА не использовать AskUserQuestion-попапы —
  варианты давать текстом нумерованным списком, пользователь отвечает цифрами.
- Пользователь шлёт замечания пакетами (5-7) со скриншотами. Цикл:
  реализовать → `node test/run.js` → поднять версии → коммит → PR → **squash-merge** → деплой.
  С 15.07 пользователь явно попросил делать squash-merge PR АВТОМАТИЧЕСКИ САМОМУ
  (не спрашивать/не ждать) — весь цикл до деплоя включительно выполняется без
  дополнительного подтверждения на каждом пакете.
- Кэш-бастинг: у каждого изменённого ассета поднять `?v=NNNN` в `index.html` (единый номер на пакет).
- После squash-merge ветка расходится с main. Паттерн:
  `git fetch origin main && git reset --hard origin/main && git cherry-pick <commit> && git push --force-with-lease`.
  ВСЕГДА коммитить до reset --hard. Ветка: `claude/full-audit-security-visualization-1fbjfm`.
- **Гайд не должен расходиться с приложением.** После КРУПНОГО/глобального изменения или
  добавления крупной функции — ОБЯЗАТЕЛЬНО проверить и актуализировать `pages/guide.html`
  (раздел «Гайд» в бургер-меню), не откладывать на потом. В коммите/PR явно отметить
  галочкой (✓), что гайд обновлён под это изменение — так же, как ниже отмечаются готовые
  пункты бэклога («— СДЕЛАН»). Мелкие правки/багфиксы такого обновления не требуют — только
  то, что реально меняет, КАК пользователь работает с приложением (новый раздел меню, новый
  режим/кнопка, новый крупный флоу). Поводом завести это правило стал разрыв: гайд много
  версий не описывал модуль «Проект квартиры» вообще и ещё 4 раздела меню (Материалы/Работа,
  Подписка, ИИ-ассистент, Админка) — обнаружилось только по прямому запросу пользователя.
- Тесты: `node test/run.js` (86 шт., без зависимостей; харнесс test/harness.js — vm-sandbox,
  cross-realm `instanceof` не работает — проверять утиными типами; DOM-атрибуты в
  fakeNode НЕ хранятся — UI-only правки в plan-unfold.js (клики/карточки) тестами
  не покрываются, только синтаксис-чек).
- Не планировать напоминания/wakeup'ы — пользователь просил без них.

## Модуль «Проект квартиры» (assets/js/modules/plan/)
Одна модель — много видов; все размеры в СМ. plan-core (модель/undo/облако),
plan-geometry (чистая математика: митра-кольца offsetRing/roomBand/insetContour,
polyWalk, wallThOf/wallMatOf — толщина/материал НА СТЕНУ через room.wallTh/wallMat[i]),
plan-canvas (viewBox-зум/пан, dragHandler с veto: return false из "start" = пан),
plan-render (штриховка паттернами userSpaceOnUse, маски проёмов, ГОСТ-символы
settings.symbolStyle), plan-rooms (режимы, тяга углов/стен, ввод длины цифрами),
plan-unfold (развёртка: fullscreen, карточка точки по двойному тапу, тяга на месте
через transform — НЕ пересобирать SVG в pointermove!), plan-routes (трассировка v4:
контур с отступом settings.routeOffset, перпендикулярные проходки Ø20 sleeveD,
макс. 2 кабеля), plan-calc (точный счёт по трассам: штробы по материалу стены,
ёмкость из EP.PoolEngine.DEFAULTS.capacity, ниша щита × модули), plan-scheme
(однолинейка через ShieldSchemeSVG: авто из p.circuits ИЛИ ручная — переключатель
режима settings.schemeMode), plan-manualscheme (ручной конструктор: группы
УЗО/Диф → линии → аппараты, дерево для ShieldSchemeSVG.renderGost, реордер
кликами прямо в SVG-предпросмотре), plan-export (печатный лист, легенда ГОСТ),
plan-rules (ПУЭ-проверки).

Ключевые инварианты:
- elemDrawPoint: отступ точки от стены = th/2+8 см, ЕДИНАЯ точка маркера и трассы.
- Цвет маркера/блока на плане (plan-render.js elemColor) = цвет ЛИНИИ QF
  (circuit.color), если она назначена элементу; иначе цвет слоя (layerColor2).
  Применено к блоку-посту (заливка rect в «Простом» стиле, stroke в ГОСТ-группе
  розеток), к одиночной точке (круг в «Простом», drawGostEl уже красил по линии)
  — просил пользователь: «цвет естественно должен зависеть от линии QF». Подпись
  высоты установки h=NNN (см) рисуется под маркером ТОЛЬКО у настенных точек
  (elem.wallId && type!=="junction" && height!=null; у свободного света/ТП/распайки
  высота=потолок — не показываем), текст НЕ повёрнут вдоль стены (всегда читается,
  class ep-plan-hlabel), показывается ВСЕГДА (не за слоем «Подписи», в отличие от
  QF-имени над точкой).
- Стиль значков (settings.symbolStyle) — ТРИ варианта, переключатель «Значки» в
  шторке 🗂 Слои (data-pr-symst, plan-rooms.js): "simple" (цветная пилюля/круг с
  буквой-глифом), "gost" (линейные ГОСТ-символы, drawGostEl) и НОВЫЙ "design"
  (drawDesignEl в plan-render.js) — рамка-квадрат с иконкой + короткая выноска
  (ep-plan-leader) к точке-«плагу» на стене (ep-plan-walldot), как на
  профессиональном чертеже (скрины пользователя). Цвет рамки/блока = цвет линии QF
  (elemColor). Рамка «Дизайна» НЕ поворачивается вдоль стены (символ всегда стоит
  вертикально, выноска сама тянется к нужной точке стены — в отличие от блока-поста
  и ГОСТ-группы, которые поворачиваются). Для блока-поста «Дизайн» добавляет только
  выноску+точку на стене, сам прямоугольник постов остаётся прежним. ОГРАНИЧЕНИЕ
  (раскрыто пользователю): в референсе цвет ЗАЛИВКИ кодирует ПОДтип розетки (умная —
  жёлтая, в пол — зелёная, в мебель — розовая), но в приложении подтипов розетки нет
  (только type:"socket") — поэтому «Дизайн» красит рамку по ЛИНИИ QF, а не по подтипу;
  подтипы розеток — отдельная модельная доработка, если понадобится.
- Размерная цепочка точек ВДОЛЬ стены на плане (расстояния между точками/проёмами
  от ВНУТРЕННИХ углов) — рисуется при включённом слое «Размеры» (dims). Логика
  вынесена в ЕДИНЫЙ хелпер G.wallChainStations(project, wall) в plan-geometry.js
  (внутр. углы thR/2 + настенные точки, приклампленные к ним + края проёмов; станция-
  точка тегируется elemId, угол/проём — elemId=null) — им пользуется И рендер
  (plan-render.js, класс ep-plan-chain/ep-plan-chaintext, БЕЗ изменения вида — тот же
  счёт, что был инлайном раньше), И двойной тап (plan-rooms.js). ВАЖНО: это НЕ новая
  цепочка — она была всегда; при пакете «символы-4» я по ошибке добавил вторую
  (от ВНЕШНИХ углов, ep-plan-eldim) — удалена, осталась одна исходная (от внутренних).
  Отступ цепочки от грани стены (off2, и в plan-render.js, и в дублирующем хит-тесте
  plan-rooms.js) — ФИКСИРОВАННЫЕ 5см в РЕАЛЬНЫХ единицах проекта (мировые см), НЕ
  зависит от зума. РАНЬШЕ считался в экранных пикселях (labelOffsetPx 14 × 2.6 × k,
  k=cmPerPx) — держал постоянный размер НА ЭКРАНЕ при любом зуме, но из-за этого
  реальный отступ в см рос при отдалении вида: на широком плане цепочка отъезжала от
  стены на десятки см и налезала на трассы/точки (репорт пользователя со скриншотами —
  «линейка отдаляется от стены при отдалении вида»; пользователь сам предложил
  фиксированные 5см — «не более, и тогда она мешать не будет»). off2 в обоих местах
  ОБЯЗАН оставаться одним и тем же числом (сейчас 5) — иначе видимая позиция цифры и
  зона двойного тапа по ней разъедутся.
- Двойной тап по ЦИФРЕ размера на плане (plan-rooms.js onDoubleTap, только режим view)
  → сразу открывает редактор ЭТОЙ точки (openEditor с полями «Отступ»/«Высота») —
  просил пользователь («хотел двойной там по размеру, и редактировать»). Два хит-теста:
  (1) подпись высоты h=NNN под маркером (позиция ~cy+(block?22:20)*k), (2) звено
  размерной цепочки — правит ДАЛЬНЮЮ точку звена (bElemId, иначе aElemId; у углов/
  проёмов elemId=null). Позиция цифры звена в хит-тесте считается ТЕМ ЖЕ off2, что и
  в рендере — общий G.wallChainStations, чтобы не разъезжались. Реализовано через
  НОВЫЙ хук canvas.onDblTap(fn) в plan-canvas.js: если
  fn вернул truthy — двойной тап «съеден», зум НЕ делается (иначе — обычный зум-к-точке,
  как раньше). Хит-тест высоты работает всегда (h=NNN рисуется всегда), звенья цепочки —
  только при включённом слое «Размеры».
- Живая легенда «Условные обозначения» (EP.Plan.Rooms.sheetLegend, кнопка
  data-pr-legend в шторке 🗂 Слои) — те же типы точек, что использованы в проекте,
  с подсчётом штук. Переиспользует EP.Plan.Export.counts(p) (вынесен и экспортирован
  из plan-export.js БЕЗ изменения — тот же счёт, что в PDF-легенде: блок раскрывается
  на items, проёмы/щиты/лента считаются отдельно из p.openings/p.panels/p.ledStrips,
  т.к. их нет в p.elements). В отличие от PDF-легенды (чёрные ГОСТ-значки для печати),
  живая — цветной чип по цвету СЛОЯ (легенда группируется по ТИПУ прибора, а не по
  линии QF), чтобы читалось на тёмной шторке (класс ep-leg/ep-leg-row/ep-leg-ic).
- Трассы НЕ идут по стене и не пересекают её, кроме перпендикулярных проходок.
- Перф: во время drag НИКОГДА не звать полный drawStrip/renderScene на каждое
  движение — только transform/атрибуты + rAF (renderSceneSoon), полный рендер на отпускании.
- Мёртвая зона тапа 7 px (иначе двойной тап не работает).
- backfillProject() в plan-core.js — ЕДИНАЯ точка бэкофилла настроек/проёмов,
  вызывается и из openProject, и из importJSON (не дублировать логику).
- Автоперестройка трасс: core().onChange слушает AUTOREBUILD_ON (elem-move/
  room-reshape/wall-th/wall-mat/beam-move/beam-w) в plan-routes.js и тихо
  зовёт build({silent:true}), если p.routes уже не пуст — новые хендлеры
  геометрии НЕ обязаны сами дёргать Routes.build(), это сделает подписка.
- Ручное редактирование трасс (route.manual:true) — тап по построенной линии
  в режиме view (routeAt/sheetRoute в plan-rooms.js, приоритет между
  вентшахтой и стеной — см. CFG.hitWallPx) открывает мини-редактор:
  🔄 Развернуть (G.flipOrthoCorner в plan-geometry.js — у ближайшего к
  тапу прямого угла P->C->N меняет местами «сначала по X/сначала по Y» на
  альтернативную вершину того же прямоугольника, null если угол не по
  осям — нечего разворачивать) и тяга (enableRouteDrag): существующий
  излом — двигаем, середина прямого участка — вставляем новый излом и сразу
  тянем его; КОНЦЫ (points[0]/points[last]) НЕ тянутся — они завязаны на
  позицию элемента/щита/распайки, редактируются только через их
  собственный редактор. Оба действия ставят route.manual:true (рендерится
  пунктиром, plan.css .ep-plan-route.is-manual) и c.persist. build() в
  plan-routes.js больше НЕ затирает ручные трассы вслепую: перед
  p.routes=[] сохраняет все manual:true в savedManual, после полной
  перестройки restoreManualRoutes() возвращает их на место — НО ТОЛЬКО
  если оба конца (anchorPos по fromId/toId — позиция панели/распайки/
  routeAnchor элемента) физически не сдвинулись (>1см — уже не округление)
  с прошлого сохранения; если анкор уехал — правка считается устаревшей,
  точка просто перестраивается заново как обычная (ЛОКАЛЬНАЯ инвалидация
  ИМЕННО этой трассы, а не сброс всех ручных трасс проекта разом — важно,
  потому что AUTOREBUILD_ON вообще не знает, КАКОЙ именно элемент
  подвинулся, глобальный флаг не сработал бы точечно). Кнопка ↺ Авто
  (EP.Plan.Routes.resetRouteToAuto(routeId)) пересчитывает ТОЛЬКО путь ЭТОЙ
  трассы (buildPath с теми же fromId/toId/toPanel, что уже были у трассы —
  топология связи узел->узел не пересматривается, только геометрия между
  теми же двумя концами) и снимает её manual. РАНЬШЕ звала полный
  build({silent:true}) целиком — а build() ВСЕГДА перестраивает С НУЛЯ
  ВСЕ не-ручные трассы проекта (restoreManualRoutes хранит только
  manual:true), поэтому клик по ↺ Авто у ОДНОЙ линии незаметно
  перетрассировывал и все остальные уже построенные авто-трассы —
  баг, пойманный экспортом проекта до/после клика от пользователя
  («когда нажимаю эту кнопку, он ещё перетрассировку делает»): три
  посторонние линии реально меняли форму пути, хотя их точки/щит/комната
  не двигались. Теперь другие трассы (ручные и автоматические) resetRouteToAuto
  вообще не трогает.
- Кнопка «⚡ Построить» (data-prt-build, plan-routes.js) — теперь
  EP.Plan.Routes.buildIncremental(), НЕ полный build(). Та же природа бага, что и
  у «↺ Авто» выше, но НЕ баг build() — build() детерминирован (проверено: повторный
  build() на identical состоянии всегда даёт identical результат) — а ожидаемое
  следствие того, что build() полностью пересчитывает С НУЛЯ вообще все не-ручные
  трассы проекта при КАЖДОМ вызове (сохраняет только route.manual:true через
  restoreManualRoutes). Расставил новые точки в одной комнате, нажал «Построить» —
  и уже готовые трассы в СОВСЕМ других комнатах незаметно меняли форму, хотя их
  точки/щит/комната не двигались (пойман тем же способом — экспорт РЕАЛЬНОГО
  проекта пользователя до/после клика, воспроизведено и проверено прогоном build()
  через тестовый харнесс на точных данных из экспорта). Пользователь ЯВНО попросил
  для ЭТОЙ кнопки другое поведение: строить трассы ТОЛЬКО для точек/распаек, у
  которых её ещё нет вообще (haveRoute = Set(routes.map(fromId))) — уже
  существующие НЕ-ручные трассы buildIncremental() вообще не трогает (ни путь, ни
  проходки), ручные (manual:true) — только recomputeThroughWalls (проходки
  актуализируются на случай, если стены/комнаты вокруг успели измениться), путь не
  трогается — это тоже была явная просьба пользователя («те трассы что уже
  отредактированы вручную, просто пересчитать без трассировки»). routeGroups()/
  routeJunctionsToPanel() — общие хелперы, вынесенные из build() БЕЗ изменения его
  поведения (build() зовёт их с pointsToRoute=ВСЕ точки, extraConnected=null —
  идентично старому коду), buildIncremental() зовёт их с pointsToRoute=ТОЛЬКО новые
  точки и extraConnected=уже проведённые точки (chainFromPanel новой точки может
  подключиться шлейфом к уже построенной РОЗЕТКЕ, а не только к щиту/распайке —
  иначе шлейф порвался бы на каждой новой точке). Полный build() (перестройка
  ВСЕХ не-ручных трасс) НАМЕРЕННО остался как есть и ОБЯЗАН оставаться — вызывается
  из AUTOREBUILD_ON (elem-move/room-reshape/…) и при смене routeOffset/сечения
  штробы в настройках: там геометрия ДЕЙСТВИТЕЛЬНО изменилась, старые трассы
  физически неточны, а не просто «трогать не нужно». Полная перестройка «с нуля»
  всё ещё доступна вручную через «✕ Очистить» + «⚡ Построить» (для пустого
  p.routes инкрементальная сборка эквивалентна полной). Кнопка «🧵» внутри
  fullscreen-развёртки (data-pu-act="trace", plan-unfold.js) тоже переведена на
  buildIncremental({silent:true}) — silent, иначе sheet() открыл бы шторку
  «Трассы» поверх fullscreen развёртки (тот же паттерн, что раньше был у build()).
- Drag-инфраструктура
  (R.canvas.setDragHandler) целиком в plan-rooms.js (как у балки/пустоты,
  ЕДИНСТВЕННОЕ место с доступом к канвасу главного вида) — plan-routes.js
  отдаёт только чтение/мутацию данных (routeAt, resetRouteToAuto), само
  выделение/тяга/подсветка (selectedRouteId(), ep-plan-routehandle-точки
  излома в plan-render.js) — в Rooms, тем же паттерном, что beamAt/sheetBeam.
- Магнит прямого угла при тяге излома трассы (G.orthoJoint в plan-geometry.js,
  вызывается из enableRouteDrag в plan-rooms.js на phase:"end") — тянущуюся
  точку имеет ДВА соседа (prev/next, оба всегда существуют — концы points[0]/
  points[last] не тянутся вообще, см. выше), каждый независимо пытается
  довести СВОЙ отрезок до вертикали/горизонтали тем же ratio-порогом
  (0.36 по умолчанию), что и у G.orthoAdjust (комнаты/балки) — если сработали
  ОБА соседа на РАЗНЫЕ оси, получается точный прямой угол (x от одного соседа,
  y от другого); если сработал только один — выравнивается только одна
  сторона ("иногда полезно", мягкий магнит, а не жёсткий constraint); если не
  сработал ни один (диагональ) — точка остаётся, где отпустили. Ось,
  зафиксированную соседом (oj.lockedX/lockedY), НЕЛЬЗЯ дополнительно округлять
  по сетке (G.snap) — округление могло бы увести уже точно совпавшую с

  целиком (иначе он ошибочно гасил бы is-full редактора при выходе ИЗ
  ЧУЖОГО fullscreen — развёртки/схемы, у которых нативный Fullscreen API
  сохранён); (2) в popstate-обработчике ветка `if (fullBox)` больше НЕ
  снимает класс — только перевзводит ловушку back-жеста (armBack()),
  полностью глотая нажатие «назад», пока открыт полный экран редактора —
  не даёт нажатию провалиться ни в закрытие шторки/режима, ни тем более в
  закрытие проекта. ЦЕНА компромисса (раскрыта пользователю): браузерный
  chrome (адресная строка) больше не скрывается, как скрывал бы настоящий
  Fullscreen API — необходимая плата за предсказуемость закрытия ТОЛЬКО
  кнопкой. Другие fullscreen-и модуля (Развёртка ⤢/🔄, Схема ⤢, шторки ⛶) НЕ
  затронуты — пользователь просил именно про полный экран главного экрана.
- Полный экран редактора: холст оставлял пустой промежуток внизу при свёрнутой
  панели инструментов (репорт пользователя со скриншотом: «съехал наверх, а не
  во весь экран»). Причина — .ep-plan-canvas в .ep-plan.is-full держал высоту
  фиксированным вычитанием (calc(100vh-215px), calc(100vh-75px) со свёрнутой
  панелью) — магическое число реальной высоте видимой шапки (.ep-plan-top) не
  соответствовало 1:1, расхождение оставалось пустым блоком снизу жёсткого
  (position:fixed;inset:0) fullscreen-контейнера. Заменено на
  `.ep-plan.is-full .ep-plan-canvas{flex:1 1 auto;min-height:0;height:auto}` —
  холст сам занимает всё оставшееся место под шапкой, без магических чисел,
  устойчиво к любой реальной высоте чужого чрома (разный масштаб текста,
  перенос кнопок и т.п.). Правило намеренно идёт ПОСЛЕ `.ep-plan.is-ctrls-
  collapsed .ep-plan-canvas` (110px, вне fullscreen — страница со своим
  скроллом, там магическое число безопасно) — та же специфичность (3 класса
  у обоих), побеждает по порядку каскада, а нужен именно flex, даже когда
  оба класса на элементе разом. Проверено вживую (headless Chromium, прямой
  mount плана): fullscreen без панели — зазор снизу холста 0px (только
  собственный padding:10px контейнера, симметричный с остальных сторон);
  раньше формула не учитывала реальную высоту шапки вовсе.
- «Во весь экран» шторки (⛶, data-sheet-fs, toggleSheetFullscreen в plan-rooms.js)
  становилась ПЛОСКИМ СЕРЫМ прямоугольником вместо тёмной полупрозрачной карточки
  на части реальных устройств (репорт пользователя: «когда раскрываю, становится
  серым» — скриншот шторки «Расчёт» в fullscreen). Причина — та же природа, что и у
  главного редактора (см. инвариант «полный экран редактора… НЕ снимался кнопками
  назад» выше), но там раньше НЕ дошли до конца: toggleSheetFullscreen() ставил
  ЧИСТЫЙ CSS-класс ep-plan-sheet-full (position:fixed) для гарантии размера, НО ВСЁ
  ЕЩЁ дополнительно звал настоящий s.requestFullscreen() «ради системного выхода
  жестом/кнопкой назад». У шторки, в отличие от .ep-plan, фон полупрозрачный
  С backdrop-filter:blur(8px) (обычная карточка, rgba(--card-bg-rgb,--card-opacity))
  — на реальных устройствах браузер иногда не может корректно скомпоновать
  backdrop-filter НА элементе, который сам является нативным fullscreen-элементом
  (top-layer), и вместо блюра полупрозрачного тёмного фона рисует элемент плоским
  серым. В headless Chromium это НЕ воспроизвелось (баг рендер-движка/GPU,
  специфичный для части реальных устройств, как и весь класс подобных багов в этой
  сессии) — фикс сделан по прямому прецеденту, не по воспроизведению. Убран сам
  вызов requestFullscreen()/exitFullscreen() ИЗ toggleSheetFullscreen() И ИЗ
  closeSheet() — теперь ЧИСТЫЙ `classList.toggle("ep-plan-sheet-full")`, без
  обращения к нативному Fullscreen API вообще (document.fullscreenElement для
  шторки больше никогда не устанавливается). Заодно удалён ставший мёртвым
  document-level `fullscreenchange`-листенер в plan-rooms.js (снимал класс шторки
  при ЛЮБОМ постороннем выходе из чужого fullscreen — больше не на что реагировать,
  тот же паттерн уборки, что и у аналогичного фикса .ep-plan). Кнопка ⛶ теперь
  переключает fullscreen шторки туда-обратно ОДНОЙ и той же кнопкой (был скрытый
  баг: обратный клик срабатывал только если `document.fullscreenElement === s`,
  т.е. только если нативный API реально успел войти в fullscreen — на устройствах,
  где он тихо не срабатывал, повторный клик вообще ничего не делал). Закрытие
  Android-«назад»/popstate (plan-mount.js) уже И РАНЬШЕ снимало класс шторки
  напрямую (`sh.classList.remove("ep-plan-sheet-full")`, не через
  fullscreenElement-проверку) — правка совместима без изменений там. Развёртка/
  Схема (⤢/🔄, plan-unfold.js/plan-scheme.js) НЕ затронуты — у них своя,
  отдельная fullscreen-логика (S.full) без backdrop-filter на самом
  fullscreen-элементе, тот класс бага там не воспроизводится, трогать не просили.
  Проверено вживую (headless Chromium, прямой mount плана + Calc.sheet()): после
  клика по ⛶ `document.fullscreenElement` остаётся null (никогда не входит в
  нативный fullscreen), класс ep-plan-sheet-full переключается туда-обратно
  ОДНОЙ кнопкой, фон/blur/текст карточки — как в обычном (не fullscreen) виде,
  тёмная полупрозрачная карточка с читаемым текстом на обоих клика.
  Слой 2 (СЛЕДУЮЩИЙ, по прямому запросу пользователя, ОТДЕЛЬНЫМ пакетом —
  затрагивает Firestore rules и админку, требует отдельного аккуратного
  прохода) — общая база контуров от ВСЕХ пользователей: submit «только
  стены и размеры» (без точек/трасс/клиента/фото) с меткой серии дома ИЛИ
  произвольным текстом (напр. «улица, дом»), модерация админом ПЕРЕД
  публикацией (в будущем — ИИ вместо ручной модерации), другие
  пользователи видят ТОЛЬКО одобренные/обезличенные шаблоны — план:
  отдельная приватная коллекция заявок (submittedBy читает только админ)
  + отдельная публичная коллекция одобренных (без submittedBy вообще, не

  правилами на чтение, только целые документы), approve копирует
  очищенные поля из заявки в публичную коллекцию.

## Оптимизация под слабые телефоны (жалоба пользователя: «фризы, подвисания»
на модуле «Проект квартиры», задача начата 18.07, план из 7 пунктов согласован
с пользователем, пункты 1-4 сделаны первым пакетом)
Аудит нашёл: КАЖДОЕ действие на плане (тап/драг-энд/сохранение поля) гоняло
подряд commit() [JSON.stringify всего проекта] → мутация → persist() [ЕЩЁ
2 JSON.stringify+localStorage.setItem: проект+индекс] → полный пересчёт
автотрасс (AUTOREBUILD_ON) → полный снос+пересборка SVG-сцены (renderScene,
масками вырезов проёмов на КАЖДУЮ комнату). Всё синхронно, в один кадр — чем
больше проект (комнат/точек/трасс/фото), тем сильнее фриз.
- **structuredClone вместо JSON.stringify/parse** в snapshot()/commit()/undo()/
  redo() (plan-core.js) — нативное глубокое клонирование объекта быстрее
  строкового round-trip (нет прохода через промежуточную JSON-строку), плюс
  undo()/redo() больше не делают повторный JSON.parse при восстановлении
  снимка (S.undo/S.redo теперь хранят живые клонированные ОБЪЕКТЫ, а не
  JSON-строки). Фолбэк `typeof structuredClone === "function" ? … :
  JSON.parse(JSON.stringify(…))` — для движков без поддержки (в т.ч. тестовый
  vm-сэндбокс test/harness.js, где structuredClone не пробрасывается в
  контекст, typeof безопасно вернёт "undefined" без ReferenceError — фолбэк
  срабатывает автоматически, тесты зелёные без правок харнесса) и на случай
  реально старых WebView на слабых телефонах — там просто останется прежнее
  (рабочее) поведение без регресса, выигрыш только там, где API есть.
- **undoLimit 100 → 40** (DEFAULTS в plan-core.js) — меньше памяти под историю
  на больших проектах (особенно с фото в el.photos — см. известное
  ограничение ниже), быстрее восстановление на undo/redo.
- **persist() debounce 400мс** (DEFAULTS.persistDebounceMs) вместо синхронной
  записи на КАЖДЫЙ вызов — persist() гоняли почти на любое действие, в т.ч. на
  "input" некоторых полей (набор текста без commit(), см. паттерн gtitle/
  lname в ручной схеме и др. — сохраняется на каждую буковку). Раньше 10
  быстрых правок подряд = 20 синхронных localStorage.setItem (10×проект +
  10×индекс); теперь коалесируются в 1 отложенную запись (подтверждено живым
  тестом: headless Chromium, 10 persist() подряд → 0 setItem сразу после
  серии, 2 setItem (проект+индекс) через 700мс). persistDirty хранит ПРЯМУЮ
  ссылку на объект проекта (не id, не повторное чтение S.project по таймеру)
  — мутации происходят на месте, поэтому к моменту срабатывания таймера в нём
  уже самые свежие данные, даже если пользователь успел переключиться на
  ДРУГОЙ проект (S.project уже другое, persistDirty всё ещё корректно
  указывает на прежний объект/id — переключение проекта не теряет и не
  портит отложенную запись прежнего). emit(what) НЕ отложен — UI и
  автоперестройка трасс (AUTOREBUILD_ON и т.п.) узнают об изменении сразу,
  откладывается только сама запись на диск/пересчёт индекса. Подстраховка от
  потери последнего действия при закрытии/сворачивании вкладки раньше 400мс —
  `visibilitychange`(hidden)/`pagehide` немедленно зовут flushPersist().
  deleteProject(id) ДОПОЛНИТЕЛЬНО гасит отложенную запись, если она как раз
  для УДАЛЯЕМОГО проекта (persistDirty.id===id) — иначе таймер воскресил бы
  только что удалённый из localStorage проект (поймано и проверено живым
  тестом: рескорректированный сценарий rename→delete до истечения 400мс —
  без гвардия проект бы вернулся в localStorage через 700мс). Проверено
  вживую (headless Chromium): serия из 10 persist() коалесируется в 1 запись;
  undo/redo корректно проходит цепочку NameC→NameB→NameA→(redo)NameB; delete
  сразу после rename не воскресает.
- Тесты (test/run.js) не тронуты по числу (151, как было) — это внутренняя
  оптимизация существующих commit/persist/undo/redo/deleteProject, поведение
  (какие данные читаются/пишутся, порядок событий) не изменилось, изменилась
  только МЕХАНИКА (клонирование, тайминг записи на диск).
- Пункт 6 плана («buildIncremental вместо build() в AUTOREBUILD_ON») ОТМЕНЁН
  при разборе — НЕПРАВИЛЬНАЯ идея, противоречит уже задокументированному выше
  инварианту: buildIncremental() пересчитывает трассы ТОЛЬКО для точек, у
  которых их ещё нет, существующие НЕ трогает вообще (ни путь, ни проходки).
  А AUTOREBUILD_ON как раз обязан пересчитать УЖЕ существующие трассы, когда
  геометрия реально изменилась (комнату/стену/перегородку подвинули) — иначе
  трассы остаются физически неточными молча (тот самый баг, что уже ловили и
  чинили раньше в build()/buildIncremental() выше). НЕ трогать эту логику.

    декоративных свечений (`.ep-plan-qmenu`, `.ep-plan-unfover`,

## Полный нагрузочный тест производительности (пакет 3, просьба пользователя:
«акцент на слабый и на самый производительный, основной функционал не должен
страдать, кешировать/внутреннее пространство/процессор на всю — делай»)
Собран синтетический стресс-проект (30 комнат по 5 точек = 150 элементов,
30 щитов, фото на 20% точек) и прогнан через headless Chromium с CDP
`Emulation.setCPUThrottlingRate` (1x — «сильный» телефон, 8x — «слабый»,
имитация бюджетного Android относительно десктопного CPU CI-контейнера).
Замерено: `renderScene()`, `Routes.build()`, `commit()`, `JSON.stringify`,
`localStorage.setItem`, и ИТОГОВАЯ цепочка «отпускание пальца после переноса
точки» (commit+mutate+persist+автоперестройка трасс+рендер — именно то, что
физически ощущается как фриз).
- **Найден и исправлен более серьёзный баг, чем фризы: реальный риск потери
  данных.** el.photos хранил base64 ПРЯМО в модели проекта (до 4 фото/точку,
  ~50-80КБ каждое после сжатия в plan-elements.js, CFG.photoSide=640/JPEG q=0.7)
  — попадал в КАЖДЫЙ undo-снимок (commit(), даже после structuredClone из
  пакета 1 — клонирование быстрее, но клонирует те же самые байты) и в КАЖДУЮ
  запись localStorage (persist()). На стресс-тесте (30 комнат, фото на 20%
  точек, ПО 180КБ/фото — заведомо больше реального сжатого размера, чтобы
  проверить границу) — `QuotaExceededError`: localStorage квота (~5-10МБ НА
  ORIGIN, ОБЩАЯ для ВСЕХ модулей приложения — не только плана) пробита.
  lsSet() после этого молча возвращает false (emit("storage-full") УЖЕ был
  подключен в plan-mount.js — маленькая текстовая подсказка в тулбаре, легко
  пропустить), и ВЕСЬ проект (не только новые фото) перестаёт сохраняться —
  реальные пользователи с несколькими десятками сфотографированных точек
  могли молча терять правки без осознания причины.
  **Фикс**: байты фото перенесены в IndexedDB (`ep_plan_photos`, квота на
  порядки больше localStorage, запись асинхронная — не блокирует поток).
  `el.photos` теперь хранит короткие id ("ph_..."), не base64. Новый блок в
  plan-core.js: `photoCache` (Map, синхронное чтение для рендера — карточка
  точки в plan-elements.js не может ждать промис на каждый показ),
  `addPhoto(dataUrl)` (кладёт в кэш СРАЗУ + фоново в IndexedDB, возвращает id
  для el.photos.push), `photoUrl(id)` (синхронное чтение из кэша),
  `migratePhotos(p)` (старые проекты с inline base64 — конвертирует в id при
  `openProject`/`importJSON`, ЕДИНАЯ точка, как и остальной бэкофилл),
  `preloadPhotos(p)` (async, грузит байты ТЕКУЩЕГО проекта из IndexedDB в
  кэш одним проходом при открытии — `openProject` теперь `await` её перед
  `emit("open")`, чтобы редактор не открылся с разбитыми картинками).
  `purgeProjectPhotos` чистит IndexedDB при удалении ВСЕГО проекта
  (`deleteProject` — НЕ отменяемое действие, чистить безопасно). НАМЕРЕННО
  НЕТ `deletePhoto()`: удаление ОДНОГО фото у точки (data-pe-phdel в
  plan-elements.js) убирает id ТОЛЬКО из el.photos (обычная undo-
  отслеживаемая мутация массива) — саму запись IndexedDB не трогаем, иначе
  Undo вернул бы id в массив, а байтов под ним уже нет (битая картинка) —
  небольшая утечка неиспользуемых записей в IndexedDB принята как цена
  корректности Undo (квота там на порядки больше, не критично).
  `exportJSON()` ГИДРИРУЕТ id ОБРАТНО в полные base64-байты ИЗ photoCache в
  ЭКСПОРТИРУЕМОЙ копии (deepClone + подмена) — экспорт уходит на другое
  устройство/браузер, где НАШЕЙ IndexedDB нет, поэтому там нужны реальные
  байты для переносимости; сам S.project (и localStorage/undo/облако)
  продолжает хранить компактные id. `importJSON()` вызывает `migratePhotos`
  синхронно (сам importJSON остаётся СИНХРОННОЙ функцией по контракту —
  тесты и вызывающий код читают возврат сразу, не await) + фоново (без await)
  `preloadPhotos` для редкого краевого случая (во входном JSON уже готовый id,
  а не data:-строка — обычным экспортом не производится, но защищаемся).
  **Побочный эффект, РАСКРЫТ пользователю как trade-off, не баг**: облачная
  синхронизация (`cloudPushSoon` → Firestore, документ ограничен 1МиБ) теперь
  пушит компактный проект (только id фото) — ОСНОВНАЯ геометрия синкается
  между устройствами НАДЁЖНЕЕ, чем раньше (inline-фото в проекте с достаточным
  числом точек и раньше могли молча пробивать 1МиБ лимит Firestore,
  best-effort `.catch(()=>false)` в cloud-store.js это тихо проглатывал — то
  есть облачный синк фото уже МОГ быть ненадёжным и до этого фикса при
  большом числе фото). ПЛАТА: сами фото — IndexedDB ЛОКАЛЬНА устройству/
  браузеру, на ДРУГОМ устройстве по id из облака их не достать (там их
  физически нет) — если нужен перенос МЕЖДУ устройствами, для этого есть
  экспорт/импорт JSON (полностью переносит фото, см. гидрацию выше), а не
  автосинхронизация.

  1500мс после монтирования канваса, за него `resize()` через ResizeObserver
  переприменяет fit() к последним осознанным параметрам) не успевало поймать
  момент, когда контейнер реально принимает финальный размер — судя по всему,
  на части реальных устройств переход в true-fullscreen PWA (или просто
  компоновка после смены на компактный тулбар пакетом выше) устаканивается
  ДОЛЬШЕ 1.5с. Ручной тоггл «Во весь экран» туда-обратно чинит это ОДНИМ явным
  вызовом `fitToProject()` (`toggleFullscreen()` в plan-mount.js) — то же самое
  теперь делается АВТОМАТИЧЕСКИ, без участия пользователя: (1) settle-окно в
  plan-canvas.js увеличено с 1500мс до 3000мс — больше времени поймать поздний
  ResizeObserver-колбэк; (2) `mountCanvas()` (plan-mount.js) ДОПОЛНИТЕЛЬНО сама
  зовёт `fitToProject()+redraw()` ЕЩЁ ДВАЖДЫ (через 400мс и 1200мс после
  монтирования) — тот же явный вызов, что и у ручного тоггла, НЕ полагаясь
  только на косвенный путь через ResizeObserver (на случай, если сам
  ResizeObserver почему-то не сработает на конкретном браузере/устройстве).
  `myCanvas`-замыкание в обоих отложенных вызовах защищает от срабатывания на
  уже пересозданном/уничтоженном канвасе (быстрый повторный заход в проект до
  истечения таймера). Проверено вживую (headless Chromium, синтетическая
  гонка: `#ep-plan-root` стартует `display:none` — `fit()` падает на аварийный
  aspect 1.5 при монтировании, — контейнер получает финальный размер только
  через 1800мс, т.е. ПОСЛЕ того, как СТАРОЕ 1500мс-окно уже закрылось бы):
  `viewBox` остаётся неверным (аварийным) вплоть до появления контейнера, а
  затем — уже к ~2200мс — корректно пересчитывается под реальные пропорции
  комнаты/контейнера — то есть НОВОЕ окно (3000мс) действительно ловит случай,
  который старое (1500мс) гарантированно пропустило бы. Полную гонку реальных
  `dvh`/true-fullscreen на живом Android-браузере headless Chromium по-прежнему
  не воспроизводит один в один (нет настоящего UI-чрома ОС) — фикс сделан по
  диагностированному механизму (тот же самый явный `fitToProject()`, что и
  доказанно работающий ручной тоггл) и прямой проверке кода, как и другие
  DOM/viewport-специфичные мобильные баги в этой сессии.

## Общие UI-утилиты (вне модуля плана)
- Полный fullscreen приложения (просьба пользователя: «хотел бы что бы было сразу во
  весь экран во всём приложении, убрать панель где отображается заряд, антенна,
  время... нижнюю панель (назад/дом/три полоски) вызывал только подтягиванием снизу
  вверх») — `manifest.webmanifest`: `display` сменён с `"standalone"` на
  `"fullscreen"` (+ `display_override:["fullscreen","standalone"]` для явного
  приоритета с грациозным откатом на браузерах без поддержки fullscreen-режима PWA).
  Это СТАНДАРТНОЕ, спецификацией предусмотренное поведение — Android/Chrome сам
  скрывает и статус-бар (заряд/антенна/часы), и системную навигационную панель
  (жест/кнопки назад-дом-обзор), возвращая их ТОЛЬКО по свайпу от края экрана и
  снова пряча — именно то поведение, что описал пользователь, никакого JS для этого
  не требуется, ОС делает это сама по манифесту. ВАЖНОЕ ОГРАНИЧЕНИЕ (раскрыто
  пользователю, не решаемо со стороны сайта): `display` в манифесте действует
  ТОЛЬКО когда приложение запущено как УСТАНОВЛЕННЫЙ PWA (значок на главном экране,
  «Добавить на главный экран» — то же меню, что использует pwa.js/`canInstall()`) —
  для обычной вкладки браузера (адресная строка, вкладки) НИ ОДИН сайт не может
  скрыть системный статус-бар/навигацию — это фундаментальное ограничение
  безопасности браузера, не обходится никаким JS-трюком; скриншоты пользователя в
  этой сессии сделаны именно в обычной вкладке браузера — эффект появится только
  после установки приложения на главный экран и запуска ИМЕННО оттуда. Тесты
  (test/run.js): обновлён существующий тест на `manifest.display` (был
  `"standalone"`, теперь `"fullscreen"`) + новая проверка `display_override`.
  ПОДТВЕРЖДЕНО пользователем на реальном устройстве (Honor/EMUI): статус-бар
  РЕАЛЬНО скрывается, НО только после ПЕРЕУСТАНОВКИ иконки на рабочем столе —
  Android «запекает» манифест в момент установки ярлыка (WebAPK) и не
  перечитывает его сразу же после каждого деплоя (аналогия с уже решённой
  проблемой кэша JS/CSS в pwa.js, только для самого манифеста автообновления
  вообще нет — обновляется только явной переустановкой: удалить иконку →
  заново «Установить приложение» через меню Chrome).
- Время/сеть/батарея ВНУТРИ шапки приложения (topbar-sysinfo.js, НОВЫЙ модуль) —
  прямой вопрос пользователя после подтверждения, что статус-бар реально
  скрывается: «можем верхний статус бар разместить так, что бы был внутри
  pwa?» (там же, в предыдущем сообщении, просил конкретно: время слева от
  имени приложения, сеть+батарея справа — освободившееся место наверху не
  пропадает впустую). Кластер РЕНДЕРИТСЯ ВСЕГДА (три новых `<span>` в
  `.topbar-title`, app-shell.js), но ВИДЕН только при `body.pwa-fullscreen`
  (CSS `display:none` по умолчанию) — класс на `<body>` ставит
  `applyPwaFullscreenClass()` через `matchMedia("(display-mode: fullscreen)")`:
  ИМЕННО `fullscreen`, не `standalone` — в `standalone`-фолбэке (браузер не
  поддержал `fullscreen` из манифеста) системный статус-бар браузер НЕ
  скрывает, значит дублировать его своим кластером не нужно, там он остаётся
  скрыт. `.topbar-title` при активном классе переключается с `justify-
  content:center` на `space-between` (три флекс-ребёнка: часы / имя / кластер
  сеть+батарея) — БЕЗ класса вёрстка не меняется вообще (часы/кластер
  `display:none`, схлопываются, видна только группа имени — 0 визуального
  риска для всех, у кого статус-бар и так браузерный). ЧЕСТНО РАСКРЫТО
  пользователю (важно не переобещать): (1) реального уровня сигнала сети
  («антенны», сколько палочек) веб-страницам браузер НЕ отдаёт ни в каком
  виде — такого API не существует физически ни в одном браузере, показываем
  лучшее реально доступное — онлайн/офлайн (`navigator.onLine`, надёжно
  везде, слушает `online`/`offline`) + тип соединения, если браузер отдаёт
  (Network Information API, `navigator.connection.effectiveType` — ТОЛЬКО
  Chromium, значения "4g"/"3g"/"2g"/"slow-2g", НЕ различает Wi-Fi от
  сотовой — такого разделения API тоже не даёт); (2) батарея —
  `navigator.getBattery()`, давно урезанный/частично удалённый из
  спецификации API — поддержка НЕ гарантирована ни на одном браузере/
  устройстве; если `typeof navigator.getBattery !== "function"` или промис
  зафейлился — элемент остаётся `hidden` молча, БЕЗ ошибки и БЕЗ выдуманных
  цифр (никогда не показываем то, что не можем измерить по-настоящему).
  Часы обновляются раз в 30с (`setInterval`, `HH:MM`, локальное время
  устройства — самый надёжный источник, permission не требует). Тесты
  (test/run.js) не тронуты по числу (162) — DOM/matchMedia-only код, как и
  остальные подобные UI-модули этой сессии (long-tip.js, consent.js), не
  покрывается vm-харнессом. Живая проверка (headless Chromium, подмена
  `matchMedia` через `page.addInitScript`): обычная вкладка (без display-mode
  override) → `body.pwa-fullscreen` НЕ ставится, часы/кластер `display:none`;
  `display-mode:fullscreen` → класс ставится, часы/кластер видны
  (`display:flex`); `display-mode:standalone` (НЕ fullscreen) → класс НЕ
  ставится, кластер скрыт — фолбэк-режим не дублирует браузерный статус-бар;
  `navigator.getBattery` застаблен на `undefined` → элемент батареи остаётся
  `hidden` без ошибок; `context.setOffline(true/false)` (реальный офлайн через
  CDP, не синтетическое событие) → текст/класс `is-offline` корректно
  переключаются в обе стороны.
- **ОТКАЧЕНО**: true-fullscreen PWA (`display:"fullscreen"` выше) — пользователь
  прямо попросил вернуть системный статус-бар видимым («верни верхний статус
  бар видным»). `manifest.webmanifest`: `display` возвращён на `"standalone"`,
  `display_override` убран целиком (был нужен только как приоритет/фолбэк для
  fullscreen, без него не нужен). Тест на `manifest.display` обновлён обратно
  на `"standalone"`, проверка `display_override` убрана из теста. Модуль
  `topbar-sysinfo.js` (часы/сеть/батарея в шапке) НЕ удалён и трогать не
  пришлось — он и раньше был спроектирован защитно: кластер виден ТОЛЬКО при
  `matchMedia("(display-mode: fullscreen)")`, а раз манифест больше не просит
  fullscreen, это условие никогда не совпадёт — кластер просто останется
  всегда скрытым сам по себе, без единой правки кода. Пустоты по краям экрана
  (два инварианта ниже) и чёрная полоса сверху были СЛЕДСТВИЕМ именно
  fullscreen-режима — с возвратом на standalone они тоже перестают быть
  актуальны для этого пользователя, но сами фиксы (100vh→100dvh и т.п.)
  оставлены как есть — универсально полезны и безвредны независимо от режима.
- Пустоты по краям экрана в true-fullscreen PWA (репорт пользователя, 3 скриншота
  с реального устройства ПОСЛЕ переустановки иконки — статус-бар уже скрыт, но
  сверху остаётся чёрная полоса, снизу у плана видна пустая область фона под
  quickbar) — найдены и заменены ПОСЛЕДНИЕ оставшиеся `100vh` в базовых
  контейнерах уровня всего приложения на `100dvh` (`.app-shell`/`.login-screen`
  в base.css, `#app`/`.app-shell`/`.page-container` в layout.css, `.ep-admin-
  page` в admin.css) — тот же принцип, что уже доказанно чинил похожие пустоты
  внутри модуля плана (`.ep-plan`, см. инвариант «Пустое пространство внизу
  холста» выше): `100vh` на мобильных исторически не гарантированно отражает
  РЕАЛЬНУЮ высоту вьюпорта при переходах между режимами отображения (обычная
  вкладка → install → true fullscreen), `100dvh` — динамический, пересчитывается
  движком под текущее состояние. Проверено (реальный Chromium, изолированный
  тест `position:fixed;inset:0` внутри `#app{zoom:N}`): САМ `zoom` (в т.ч. !=1)
  НЕ ломает `position:fixed;inset:0` — под подозрением была ТОЛЬКО `#app{zoom:
  var(--font-scale,1)}` (base.css) как потенциальный «похититель» containing
  block для fixed-потомков (`.app-bg`), гипотеза ПРОВЕРЕНА И ОТКЛОНЕНА отдельным
  тестом — `.app-bg{position:fixed;inset:0}` устойчиво покрывает РЕАЛЬНЫЙ
  вьюпорт независимо от zoom родителя, менять `#app{zoom:...}` не потребовалось.
  ЧЕСТНО РАСКРЫТО пользователю (не решаемо со стороны сайта, судя по анализу):
  сплошная ЧЁРНАЯ (не наш градиент `.app-bg`) полоса СВЕРХУ на всех 3 скриншотах,
  ПОВЕРХ вообще любого контента приложения (в т.ч. выше собственного топбара) —
  не укладывается в модель «наш CSS не дотягивается до края», т.к. `.app-bg`
  (`position:fixed;inset:0`, `viewport-fit=cover` уже стоит в meta viewport)
  ДОЛЖЕН технически всегда доставать до истинного верха экрана независимо от
  `vh`/`dvh` — если полоса всё равно чёрная (не наш градиент), скорее всего это
  РЕЗЕРВ САМОЙ ОС/WebView под эту зону (жест «потянуть для статус-бара»/область
  выреза камеры, которую конкретно этот OEM (Honor/Magic UI) рисует чёрным
  ВМЕСТО того, чтобы отдать её содержимому страницы) — то есть ограничение
  конкретной прошивки/браузера, а не баг кода приложения. `100vh→100dvh` фикс
  всё равно оставлен — безопасен всегда, и может частично помочь с НИЖНИМИ/
  боковыми пустотами (где контент действительно не дотягивался до реальной
  доступной высоты), даже если верхнюю чёрную полосу не решает. Тесты
  (test/run.js) не тронуты по числу (162) — чистая CSS-правка величин, не
  затрагивающая структуру, которую проверяют тесты.
- УТОЧНЕНИЕ к пункту выше — пользователь подтвердил (цифрой): пустоты «по бокам»
  на шторках «Проверки»/«Расчёт» БЫЛИ ДАЖЕ ПОСЛЕ нажатия ⛶ (т.е. уже в состоянии
  `.ep-plan-sheet-full`, не в обычном виде, где узкие поля по 8px — ожидаемы по
  дизайну). НАЙДЕН РЕАЛЬНЫЙ БАГ в самом `.ep-plan-sheet-full` (plan.css): помимо
  `position:fixed!important;inset:0!important` (которое САМО ПО СЕБЕ, по спецификации
  CSS, гарантированно растягивает блок ровно на границы containing block — проверено
  отдельным тестом реальный Chromium: `position:fixed;inset:0` без явных width/height
  всегда точно совпадает с `window.innerWidth/innerHeight`, независимо от vh/vw/dvh),
  правило ДОПОЛНИТЕЛЬНО дублировало размер через `width:100vw!important;100dvw!important;
  height:100vh!important;100dvh!important;max-height:100vh!important;100dvh!important`.
  Эти явные vh/vw-декларации С `!important` ПЕРЕБИВАЛИ собой честный edge-to-edge
  размер, который дал бы один `inset:0` — если на конкретном устройстве/прошивке
  `vh`/`dvh`/`vw`/`dvw` недооценивают истинный вьюпорт в true-fullscreen PWA (та же
  природа проблемы, что уже подозревалась в предыдущем пункте выше про чёрную полосу
  сверху), то ИМЕННО эти лишние декларации активно СЖИМАЛИ шторку до заниженного
  размера — сам `inset:0` был бы полностью иммунен к этой проблеме. Убраны width/
  height/vw/vh-декларации целиком, `max-height` заменён на `max-height:100%!important`
  (процентный, считается от того же самого containing block, что уже задал `inset:0`
  — не может с ним разойтись, в отличие от независимо вычисляемого vh/dvh). Проверено
  вживую (headless Chromium, изолированный тест `.ep-plan-sheet.ep-plan-sheet-full`
  вне контекста плана): `getBoundingClientRect()` точно совпадает с `window.
  innerWidth/innerHeight` — 0 регрессии для устройств, где `dvh` и так был точным
  (headless Chromium в их числе, поэтому баг НЕ воспроизводится автоматизированным
  тестом «до/после» — сама природа бага требует расхождения vh/dvh с истинным
  вьюпортом, которое возможно ТОЛЬКО на конкретных реальных устройствах, не в
  тестовой песочнице; фикс сделан по логическому разбору CSS-спецификации, а не по

- Автообновление PWA (pwa.js) — просьба пользователя: «как сделать чтобы кэш обновлялся
  автоматически? иначе иногда цепляется за предыдущее». Раньше `pwa.js` только
  регистрировал `sw.js` (`navigator.serviceWorker.register`) и ничего больше не делал —
  service worker в браузере проверяется на новую версию не чаще раза в ~24ч (throttle

  редко (обычные деплои меняют только JS/CSS/index.html) — значит для подавляющего
  большинства деплоев вообще НЕ было события, на которое приложение могло бы среагировать:
  открытая вкладка/установленное PWA держит СТАРЫЙ уже выполняющийся в памяти JS
  сколько угодно, пока пользователь сам не сделает полный ручной reload. Добавлено ДВА
  независимых механизма детекта, оба сходятся в одном безопасном reload():
  (1) versionFingerprint() — сравнивает набор `?v=NNNN` у `<script>/<link>` уже
  загруженной страницы (снятый ОДИН раз при старте, `document.documentElement.outerHTML`
  в момент выполнения `defer`-скрипта — DOM уже полностью распарсен к этому моменту) со
  свежим `/index.html` (`{cache:"no-store"}`, тот же URL, что сервер всегда отдаёт по
  последнему деплою) — ловит ЛЮБОЙ обычный деплой контента, не только смену sw.js;
  (2) `swReg.update()` форсирует проверку sw.js раньше браузерного 24ч-таймера — на
  случай, если сам sw.js когда-то изменится (кэш-стратегия и т.п.), плюс
  `controllerchange` (новый SW сам себя активирует — `skipWaiting()+clients.claim()` уже
  были в sw.js) не обновляет уже выполняющийся JS страницы без явного reload(). Обе
  проверки — throttled до раза в минуту, запускаются на КАЖДЫЙ возврат в приложение
  (`visibilitychange` → `"visible"`) — самый частый в реальности триггер устаревания:
  вкладка/PWA висела в фоне или была закрыта, открыли заново. Reload НЕ дёргается, пока
  пользователь СМОТРИТ на экран (мог бы сбросить незакоммиченный жест — драг точки на
  плане и т.п., хоть данные и не теряются, они коммитятся отдельно) — если апдейт
  обнаружен, пока вкладка видима, `pendingReload` откладывает reload() до СЛЕДУЮЩЕГО
  ухода в фон (`visibilitychange` → `"hidden"`) — к моменту возврата пользователь уже
  увидит свежую версию без единого заметного скачка. Тесты (headless Chromium,
  подмена `window.fetch` для `/index.html` + ручной диспатч `visibilitychange` с
  переопределённым `document.visibilityState`, счётчик `page.on("load")` вместо попытки
  подменить `location.reload` — она НЕ configurable в реальном Chromium, попытка
  переопределить тихо падает): одинаковый контент при возврате → reload НЕ вызван;
  другой контент, вкладка остаётся видимой → reload НЕ вызван (отложен); тот же случай,
  затем вкладка уходит в фон → reload вызван (второй `page.on("load")`). ОДНОРАЗОВОЕ
  ограничение при переходе (не баг, неизбежно): у КОГО-ТО уже открыта вкладка со СТАРЫМ
  `pwa.js` (без этой логики) в момент, когда фикс выкатывается, — сама эта вкладка
  обновится этим механизмом только один раз ЕЩЁ вручную/по факту следующего обычного
  reload; уже ПОСЛЕ этого перехода механизм работает сам на все последующие деплои.

Пустое пространство внизу холста (репорт пользователя, 2 скриншота: свёрнутая
панель инструментов И обычная не-fullscreen шторка «Печатный лист (PDF)» — «это
не только на расчёте, а во всех функциях») — НЕ регресс фикса fullscreen-шторок
(тот отдельная, не связанная механика), а более общий, ранее не пойманный баг
самого БАЗОВОГО холста `.ep-plan-canvas` ВНЕ fullscreen:
- Раньше `.ep-plan-canvas` вычитал магические числа из 100vh/100dvh:
  `calc(100vh-250px)` в обычном виде, `calc(100vh-110px)` при свёрнутой панели
  инструментов (`.is-ctrls-collapsed`). Комментарий рядом утверждал «вне
  fullscreen страница сама скроллится, магическое число безопасно» — ЛОЖНОЕ
  предположение: если calc() ВЫЧИТАЕТ БОЛЬШЕ реальной высоты шапки (а не
  меньше), холст получается КОРОЧЕ доступного места, и лишнее пространство
  просто пустует НИЖЕ холста (нечему скроллиться — страница и так короче
  экрана) — ровно то, что видно на обоих скриншотах пользователя: пустой
  белый хвост под свёрнутой панелью И под обычной (не fullscreen) шторкой,
  где должен быть виден холст сквозь/вокруг неё.
- Фикс — тот же принцип, что уже доказанно работает у `.ep-plan.is-full`
  (flex вместо calc с магическим числом), но БЕЗ position:fixed (вне
  fullscreen холст обязан оставаться в потоке страницы — топбар/бургер-меню
  должны быть доступны, в отличие от fullscreen). `.ep-plan` (уже
  `display:flex;flex-direction:column`) получил `min-height: calc(100dvh -
  var(--topbar-h) - 40px)` — `--topbar-h` РЕАЛЬНАЯ CSS-переменная (32-36px по
  density-настройке), НЕ магическое число, тот же источник, что уже двигает
  `.app-shell`/`.page-container`; 40px — небольшой, терпимый запас (паддинги
  `.page-container` 6+22 + доп. 8px у `.app-shell`) — небольшая неточность
  тут даёт лишь пару px лишнего скролла страницы, не огромный пустой блок.
  `.ep-plan-canvas` (БАЗОВОЕ правило, не только is-full) — `flex:1 1 auto;
  min-height:320px;height:auto` вместо calc(). Правило
  `.ep-plan.is-ctrls-collapsed .ep-plan-canvas{height:calc(...)}` УДАЛЕНО
  целиком — больше не нужно: flex-grow сам съедает освободившееся от
  свёрнутого тулбара место, скрыт тулбар или нет, БЕЗ отдельного магического
  числа на этот случай. `.ep-plan.is-full .ep-plan-canvas{flex:1 1 auto;
  min-height:0;...}` не тронут (там `.ep-plan.is-full` сам `position:fixed;
  inset:0`, полностью замкнут вьюпортом — новый `min-height` у базового
  `.ep-plan` там ни на что не влияет, высота уже однозначно задана инсетами).
- Проверено вживую (headless Chromium, реальный `EP.AppShell.render()` — с
  топбаром, не изолированно): зазор холста внутри `.ep-plan` (`gapBelow
  CanvasWithinPlan`) = 0px во ВСЕХ трёх сценариях (обычный вид, свёрнутая

  вьюпорта стабильно ~26px (естественный паддинг страницы, не аномалия) на

  722px высоты при сворачивании панели, забирая ровно освободившееся место).
- Заодно у «Печатный лист (PDF)» (plan-export.js `sheetPdfScale()`) добавлена
  кнопка ⛶ (`data-sheet-fs`) — единственная содержательная шторка модуля
