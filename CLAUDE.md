# Electric Pro V29 — правила работы для Claude

PWA для электриков (RU). Vanilla JS (ES2020), IIFE-модули в `window.EP.*`, БЕЗ сборки,
БЕЗ TypeScript/React — не переписывать. Firebase Hosting/Auth/Firestore. Деплой:
push в `main` → GitHub Actions (`firebase-deploy.yml`) → синтакс-чек + `node test/run.js`
(гейт) → Firebase. APK-путь: PWA + TWA/Capacitor (см. docs/APK.md).

## Процесс (выработан с пользователем)
- Общение по-русски. НИКОГДА не использовать AskUserQuestion-попапы —
  варианты давать текстом нумерованным списком, пользователь отвечает цифрами.
- Пользователь шлёт замечания пакетами (5-7) со скриншотами. Цикл:
  реализовать → `node test/run.js` → поднять версии → коммит → PR → **squash-merge** → деплой.
  С 15.07 пользователь явно попросил делать squash-merge PR АВТОМАТИЧЕСКИ САМОМУ
  (не спрашивать/не ждать) — весь цикл до деплоя включительно выполняется без
  дополнительного подтверждения на каждом пакете.
- Кэш-бастинг: у каждого изменённого ассета поднять `?v=NNNN` в `index.html` (единый номер на пакет).
- После squash-merge ветка расходится с main. Паттерн:
  `git fetch origin main && git reset --hard origin/main && git cherry-pick <commit> && git push --force-with-lease`.
  ВСЕГДА коммитить до reset --hard. Ветка: `claude/full-audit-security-visualization-1fbjfm`.
- **Гайд не должен расходиться с приложением.** После КРУПНОГО/глобального изменения или
  добавления крупной функции — ОБЯЗАТЕЛЬНО проверить и актуализировать `pages/guide.html`
  (раздел «Гайд» в бургер-меню), не откладывать на потом. В коммите/PR явно отметить
  галочкой (✓), что гайд обновлён под это изменение — так же, как ниже отмечаются готовые
  пункты бэклога («— СДЕЛАН»). Мелкие правки/багфиксы такого обновления не требуют — только
  то, что реально меняет, КАК пользователь работает с приложением (новый раздел меню, новый
  режим/кнопка, новый крупный флоу). Поводом завести это правило стал разрыв: гайд много
  версий не описывал модуль «Проект квартиры» вообще и ещё 4 раздела меню (Материалы/Работа,
  Подписка, ИИ-ассистент, Админка) — обнаружилось только по прямому запросу пользователя.
- Тесты: `node test/run.js` (86 шт., без зависимостей; харнесс test/harness.js — vm-sandbox,
  cross-realm `instanceof` не работает — проверять утиными типами; DOM-атрибуты в
  fakeNode НЕ хранятся — UI-only правки в plan-unfold.js (клики/карточки) тестами
  не покрываются, только синтаксис-чек).
- Не планировать напоминания/wakeup'ы — пользователь просил без них.

## Модуль «Проект квартиры» (assets/js/modules/plan/)
Одна модель — много видов; все размеры в СМ. plan-core (модель/undo/облако),
plan-geometry (чистая математика: митра-кольца offsetRing/roomBand/insetContour,
polyWalk, wallThOf/wallMatOf — толщина/материал НА СТЕНУ через room.wallTh/wallMat[i]),
plan-canvas (viewBox-зум/пан, dragHandler с veto: return false из "start" = пан),
plan-render (штриховка паттернами userSpaceOnUse, маски проёмов, ГОСТ-символы
settings.symbolStyle), plan-rooms (режимы, тяга углов/стен, ввод длины цифрами),
plan-unfold (развёртка: fullscreen, карточка точки по двойному тапу, тяга на месте
через transform — НЕ пересобирать SVG в pointermove!), plan-routes (трассировка v4:
контур с отступом settings.routeOffset, перпендикулярные проходки Ø20 sleeveD,
макс. 2 кабеля), plan-calc (точный счёт по трассам: штробы по материалу стены,
ёмкость из EP.PoolEngine.DEFAULTS.capacity, ниша щита × модули), plan-scheme
(однолинейка через ShieldSchemeSVG: авто из p.circuits ИЛИ ручная — переключатель
режима settings.schemeMode), plan-manualscheme (ручной конструктор: группы
УЗО/Диф → линии → аппараты, дерево для ShieldSchemeSVG.renderGost, реордер
кликами прямо в SVG-предпросмотре), plan-export (печатный лист, легенда ГОСТ),
plan-rules (ПУЭ-проверки).

Ключевые инварианты:
- elemDrawPoint: отступ точки от стены = th/2+8 см, ЕДИНАЯ точка маркера и трассы.
- Цвет маркера/блока на плане (plan-render.js elemColor) = цвет ЛИНИИ QF
  (circuit.color), если она назначена элементу; иначе цвет слоя (layerColor2).
  Применено к блоку-посту (заливка rect в «Простом» стиле, stroke в ГОСТ-группе
  розеток), к одиночной точке (круг в «Простом», drawGostEl уже красил по линии)
  — просил пользователь: «цвет естественно должен зависеть от линии QF». Подпись
  высоты установки h=NNN (см) рисуется под маркером ТОЛЬКО у настенных точек
  (elem.wallId && type!=="junction" && height!=null; у свободного света/ТП/распайки
  высота=потолок — не показываем), текст НЕ повёрнут вдоль стены (всегда читается,
  class ep-plan-hlabel), показывается ВСЕГДА (не за слоем «Подписи», в отличие от
  QF-имени над точкой).
- Стиль значков (settings.symbolStyle) — ТРИ варианта, переключатель «Значки» в
  шторке 🗂 Слои (data-pr-symst, plan-rooms.js): "simple" (цветная пилюля/круг с
  буквой-глифом), "gost" (линейные ГОСТ-символы, drawGostEl) и НОВЫЙ "design"
  (drawDesignEl в plan-render.js) — рамка-квадрат с иконкой + короткая выноска
  (ep-plan-leader) к точке-«плагу» на стене (ep-plan-walldot), как на
  профессиональном чертеже (скрины пользователя). Цвет рамки/блока = цвет линии QF
  (elemColor). Рамка «Дизайна» НЕ поворачивается вдоль стены (символ всегда стоит
  вертикально, выноска сама тянется к нужной точке стены — в отличие от блока-поста
  и ГОСТ-группы, которые поворачиваются). Для блока-поста «Дизайн» добавляет только
  выноску+точку на стене, сам прямоугольник постов остаётся прежним. ОГРАНИЧЕНИЕ
  (раскрыто пользователю): в референсе цвет ЗАЛИВКИ кодирует ПОДтип розетки (умная —
  жёлтая, в пол — зелёная, в мебель — розовая), но в приложении подтипов розетки нет
  (только type:"socket") — поэтому «Дизайн» красит рамку по ЛИНИИ QF, а не по подтипу;
  подтипы розеток — отдельная модельная доработка, если понадобится.
- Размерная цепочка точек ВДОЛЬ стены на плане (расстояния между точками/проёмами
  от ВНУТРЕННИХ углов) — рисуется при включённом слое «Размеры» (dims). Логика
  вынесена в ЕДИНЫЙ хелпер G.wallChainStations(project, wall) в plan-geometry.js
  (внутр. углы thR/2 + настенные точки, приклампленные к ним + края проёмов; станция-
  точка тегируется elemId, угол/проём — elemId=null) — им пользуется И рендер
  (plan-render.js, класс ep-plan-chain/ep-plan-chaintext, БЕЗ изменения вида — тот же
  счёт, что был инлайном раньше), И двойной тап (plan-rooms.js). ВАЖНО: это НЕ новая
  цепочка — она была всегда; при пакете «символы-4» я по ошибке добавил вторую
  (от ВНЕШНИХ углов, ep-plan-eldim) — удалена, осталась одна исходная (от внутренних).
- Двойной тап по ЦИФРЕ размера на плане (plan-rooms.js onDoubleTap, только режим view)
  → сразу открывает редактор ЭТОЙ точки (openEditor с полями «Отступ»/«Высота») —
  просил пользователь («хотел двойной там по размеру, и редактировать»). Два хит-теста:
  (1) подпись высоты h=NNN под маркером (позиция ~cy+(block?22:20)*k), (2) звено
  размерной цепочки — правит ДАЛЬНЮЮ точку звена (bElemId, иначе aElemId; у углов/
  проёмов elemId=null). Позиция цифры звена в хит-тесте считается ТЕМ ЖЕ off2
  (labelOffsetPx 14 × 2.6 × k), что и в рендере — общий G.wallChainStations, чтобы не
  разъезжались. Реализовано через НОВЫЙ хук canvas.onDblTap(fn) в plan-canvas.js: если
  fn вернул truthy — двойной тап «съеден», зум НЕ делается (иначе — обычный зум-к-точке,
  как раньше). Хит-тест высоты работает всегда (h=NNN рисуется всегда), звенья цепочки —
  только при включённом слое «Размеры».
- Живая легенда «Условные обозначения» (EP.Plan.Rooms.sheetLegend, кнопка
  data-pr-legend в шторке 🗂 Слои) — те же типы точек, что использованы в проекте,
  с подсчётом штук. Переиспользует EP.Plan.Export.counts(p) (вынесен и экспортирован
  из plan-export.js БЕЗ изменения — тот же счёт, что в PDF-легенде: блок раскрывается
  на items, проёмы/щиты/лента считаются отдельно из p.openings/p.panels/p.ledStrips,
  т.к. их нет в p.elements). В отличие от PDF-легенды (чёрные ГОСТ-значки для печати),
  живая — цветной чип по цвету СЛОЯ (легенда группируется по ТИПУ прибора, а не по
  линии QF), чтобы читалось на тёмной шторке (класс ep-leg/ep-leg-row/ep-leg-ic).
- Трассы НЕ идут по стене и не пересекают её, кроме перпендикулярных проходок.
- Перф: во время drag НИКОГДА не звать полный drawStrip/renderScene на каждое
  движение — только transform/атрибуты + rAF (renderSceneSoon), полный рендер на отпускании.
- Мёртвая зона тапа 7 px (иначе двойной тап не работает).
- backfillProject() в plan-core.js — ЕДИНАЯ точка бэкофилла настроек/проёмов,
  вызывается и из openProject, и из importJSON (не дублировать логику).
- Автоперестройка трасс: core().onChange слушает AUTOREBUILD_ON (elem-move/
  room-reshape/wall-th/wall-mat/beam-move/beam-w) в plan-routes.js и тихо
  зовёт build({silent:true}), если p.routes уже не пуст — новые хендлеры
  геометрии НЕ обязаны сами дёргать Routes.build(), это сделает подписка.
- Ручное редактирование трасс (route.manual:true) — тап по построенной линии
  в режиме view (routeAt/sheetRoute в plan-rooms.js, приоритет между
  вентшахтой и стеной — см. CFG.hitWallPx) открывает мини-редактор:
  🔄 Развернуть (G.flipOrthoCorner в plan-geometry.js — у ближайшего к
  тапу прямого угла P->C->N меняет местами «сначала по X/сначала по Y» на
  альтернативную вершину того же прямоугольника, null если угол не по
  осям — нечего разворачивать) и тяга (enableRouteDrag): существующий
  излом — двигаем, середина прямого участка — вставляем новый излом и сразу
  тянем его; КОНЦЫ (points[0]/points[last]) НЕ тянутся — они завязаны на
  позицию элемента/щита/распайки, редактируются только через их
  собственный редактор. Оба действия ставят route.manual:true (рендерится
  пунктиром, plan.css .ep-plan-route.is-manual) и c.persist. build() в
  plan-routes.js больше НЕ затирает ручные трассы вслепую: перед
  p.routes=[] сохраняет все manual:true в savedManual, после полной
  перестройки restoreManualRoutes() возвращает их на место — НО ТОЛЬКО
  если оба конца (anchorPos по fromId/toId — позиция панели/распайки/
  routeAnchor элемента) физически не сдвинулись (>1см — уже не округление)
  с прошлого сохранения; если анкор уехал — правка считается устаревшей,
  точка просто перестраивается заново как обычная (ЛОКАЛЬНАЯ инвалидация
  ИМЕННО этой трассы, а не сброс всех ручных трасс проекта разом — важно,
  потому что AUTOREBUILD_ON вообще не знает, КАКОЙ именно элемент
  подвинулся, глобальный флаг не сработал бы точечно). Кнопка ↺ Авто
  (EP.Plan.Routes.resetRouteToAuto(routeId)) пересчитывает ТОЛЬКО путь ЭТОЙ
  трассы (buildPath с теми же fromId/toId/toPanel, что уже были у трассы —
  топология связи узел->узел не пересматривается, только геометрия между
  теми же двумя концами) и снимает её manual. РАНЬШЕ звала полный
  build({silent:true}) целиком — а build() ВСЕГДА перестраивает С НУЛЯ
  ВСЕ не-ручные трассы проекта (restoreManualRoutes хранит только
  manual:true), поэтому клик по ↺ Авто у ОДНОЙ линии незаметно
  перетрассировывал и все остальные уже построенные авто-трассы —
  баг, пойманный экспортом проекта до/после клика от пользователя
  («когда нажимаю эту кнопку, он ещё перетрассировку делает»): три
  посторонние линии реально меняли форму пути, хотя их точки/щит/комната
  не двигались. Теперь другие трассы (ручные и автоматические) resetRouteToAuto
  вообще не трогает.
- Кнопка «⚡ Построить» (data-prt-build, plan-routes.js) — теперь
  EP.Plan.Routes.buildIncremental(), НЕ полный build(). Та же природа бага, что и
  у «↺ Авто» выше, но НЕ баг build() — build() детерминирован (проверено: повторный
  build() на identical состоянии всегда даёт identical результат) — а ожидаемое
  следствие того, что build() полностью пересчитывает С НУЛЯ вообще все не-ручные
  трассы проекта при КАЖДОМ вызове (сохраняет только route.manual:true через
  restoreManualRoutes). Расставил новые точки в одной комнате, нажал «Построить» —
  и уже готовые трассы в СОВСЕМ других комнатах незаметно меняли форму, хотя их
  точки/щит/комната не двигались (пойман тем же способом — экспорт РЕАЛЬНОГО
  проекта пользователя до/после клика, воспроизведено и проверено прогоном build()
  через тестовый харнесс на точных данных из экспорта). Пользователь ЯВНО попросил
  для ЭТОЙ кнопки другое поведение: строить трассы ТОЛЬКО для точек/распаек, у
  которых её ещё нет вообще (haveRoute = Set(routes.map(fromId))) — уже
  существующие НЕ-ручные трассы buildIncremental() вообще не трогает (ни путь, ни
  проходки), ручные (manual:true) — только recomputeThroughWalls (проходки
  актуализируются на случай, если стены/комнаты вокруг успели измениться), путь не
  трогается — это тоже была явная просьба пользователя («те трассы что уже
  отредактированы вручную, просто пересчитать без трассировки»). routeGroups()/
  routeJunctionsToPanel() — общие хелперы, вынесенные из build() БЕЗ изменения его
  поведения (build() зовёт их с pointsToRoute=ВСЕ точки, extraConnected=null —
  идентично старому коду), buildIncremental() зовёт их с pointsToRoute=ТОЛЬКО новые
  точки и extraConnected=уже проведённые точки (chainFromPanel новой точки может
  подключиться шлейфом к уже построенной РОЗЕТКЕ, а не только к щиту/распайке —
  иначе шлейф порвался бы на каждой новой точке). Полный build() (перестройка
  ВСЕХ не-ручных трасс) НАМЕРЕННО остался как есть и ОБЯЗАН оставаться — вызывается
  из AUTOREBUILD_ON (elem-move/room-reshape/…) и при смене routeOffset/сечения
  штробы в настройках: там геометрия ДЕЙСТВИТЕЛЬНО изменилась, старые трассы
  физически неточны, а не просто «трогать не нужно». Полная перестройка «с нуля»
  всё ещё доступна вручную через «✕ Очистить» + «⚡ Построить» (для пустого
  p.routes инкрементальная сборка эквивалентна полной). Кнопка «🧵» внутри
  fullscreen-развёртки (data-pu-act="trace", plan-unfold.js) тоже переведена на
  buildIncremental({silent:true}) — silent, иначе sheet() открыл бы шторку
  «Трассы» поверх fullscreen развёртки (тот же паттерн, что раньше был у build()).
- Drag-инфраструктура
  (R.canvas.setDragHandler) целиком в plan-rooms.js (как у балки/пустоты,
  ЕДИНСТВЕННОЕ место с доступом к канвасу главного вида) — plan-routes.js
  отдаёт только чтение/мутацию данных (routeAt, resetRouteToAuto), само
  выделение/тяга/подсветка (selectedRouteId(), ep-plan-routehandle-точки
  излома в plan-render.js) — в Rooms, тем же паттерном, что beamAt/sheetBeam.
- Магнит прямого угла при тяге излома трассы (G.orthoJoint в plan-geometry.js,
  вызывается из enableRouteDrag в plan-rooms.js на phase:"end") — тянущуюся
  точку имеет ДВА соседа (prev/next, оба всегда существуют — концы points[0]/
  points[last] не тянутся вообще, см. выше), каждый независимо пытается
  довести СВОЙ отрезок до вертикали/горизонтали тем же ratio-порогом
  (0.36 по умолчанию), что и у G.orthoAdjust (комнаты/балки) — если сработали
  ОБА соседа на РАЗНЫЕ оси, получается точный прямой угол (x от одного соседа,
  y от другого); если сработал только один — выравнивается только одна
  сторона ("иногда полезно", мягкий магнит, а не жёсткий constraint); если не
  сработал ни один (диагональ) — точка остаётся, где отпустили. Ось,
  зафиксированную соседом (oj.lockedX/lockedY), НЕЛЬЗЯ дополнительно округлять
  по сетке (G.snap) — округление могло бы увести уже точно совпавшую с
  соседом координату; округляется по сетке только СВОБОДНАЯ ось. Кнопка
  🧮 Пересчитать в редакторе трассы (data-prt2-calc, рядом с 🔄/↺ Авто)
  закрывает редактор трассы и сразу открывает шторку «Расчёт»
  (EP.Plan.Calc.sheet()) — своей отдельной логики пересчёта НЕ потребовалось,
  Calc.sheet()/calcByRoutes() и так всегда пересчитывают заново по текущему
  p.routes при каждом открытии (никакого кэша нет) — кнопка чисто
  навигационная, чтобы не выходить в меню после правки трассы вручную.
- Коннекторы (ВАГО/ГМЛ/СИЗ): pin-count распайки = ТОЧНОЕ число сходящихся
  кабелей (inCnt+outCnt по графу трасс) — точнее, чем в pool-engine.
- wallAt: у ОБЩЕЙ стены двух комнат centerline совпадает — раньше побеждала
  всегда первая комната. Теперь через wallFrame.nrm сравниваем, В СТОРОНУ
