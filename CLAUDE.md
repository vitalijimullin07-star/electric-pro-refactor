# Electric Pro V29 — правила работы для Claude

PWA для электриков (RU). Vanilla JS (ES2020), IIFE-модули в `window.EP.*`, БЕЗ сборки,
БЕЗ TypeScript/React — не переписывать. Firebase Hosting/Auth/Firestore. Деплой:
push в `main` → GitHub Actions (`firebase-deploy.yml`) → синтакс-чек + `node test/run.js`
(гейт) → Firebase. APK-путь: PWA + TWA/Capacitor (см. docs/APK.md).

## Процесс (выработан с пользователем)
- Общение по-русски. НИКОГДА не использовать AskUserQuestion-попапы —
  варианты давать текстом нумерованным списком, пользователь отвечает цифрами.
- Пользователь шлёт замечания пакетами (5-7) со скриншотами. Цикл:
  реализовать → `node test/run.js` → поднять версии → коммит → PR → **squash-merge** → деплой сам.
- Кэш-бастинг: у каждого изменённого ассета поднять `?v=NNNN` в `index.html` (единый номер на пакет).
- После squash-merge ветка расходится с main. Паттерн:
  `git fetch origin main && git reset --hard origin/main && git cherry-pick <commit> && git push --force-with-lease`.
  ВСЕГДА коммитить до reset --hard. Ветка: `claude/full-audit-security-visualization-1fbjfm`.
- Тесты: `node test/run.js` (78 шт., без зависимостей; харнесс test/harness.js — vm-sandbox,
  cross-realm `instanceof` не работает — проверять утиными типами; DOM-атрибуты в
  fakeNode НЕ хранятся — UI-only правки в plan-unfold.js (клики/карточки) тестами
  не покрываются, только синтаксис-чек).
- Не планировать напоминания/wakeup'ы — пользователь просил без них.

## Модуль «Проект квартиры» (assets/js/modules/plan/)
Одна модель — много видов; все размеры в СМ. plan-core (модель/undo/облако),
plan-geometry (чистая математика: митра-кольца offsetRing/roomBand/insetContour,
polyWalk, wallThOf/wallMatOf — толщина/материал НА СТЕНУ через room.wallTh/wallMat[i]),
plan-canvas (viewBox-зум/пан, dragHandler с veto: return false из "start" = пан),
plan-render (штриховка паттернами userSpaceOnUse, маски проёмов, ГОСТ-символы
settings.symbolStyle), plan-rooms (режимы, тяга углов/стен, ввод длины цифрами),
plan-unfold (развёртка: fullscreen, карточка точки по двойному тапу, тяга на месте
через transform — НЕ пересобирать SVG в pointermove!), plan-routes (трассировка v4:
контур с отступом settings.routeOffset, перпендикулярные проходки Ø20 sleeveD,
макс. 2 кабеля), plan-calc (точный счёт по трассам: штробы по материалу стены,
ёмкость из EP.PoolEngine.DEFAULTS.capacity, ниша щита × модули), plan-scheme
(однолинейка через ShieldSchemeSVG: авто из p.circuits ИЛИ ручная — переключатель
режима settings.schemeMode), plan-manualscheme (ручной конструктор: группы
УЗО/Диф → линии → аппараты, дерево для ShieldSchemeSVG.renderGost, реордер
кликами прямо в SVG-предпросмотре), plan-export (печатный лист, легенда ГОСТ),
plan-rules (ПУЭ-проверки).

Ключевые инварианты:
- elemDrawPoint: отступ точки от стены = th/2+8 см, ЕДИНАЯ точка маркера и трассы.
- Трассы НЕ идут по стене и не пересекают её, кроме перпендикулярных проходок.
- Перф: во время drag НИКОГДА не звать полный drawStrip/renderScene на каждое
  движение — только transform/атрибуты + rAF (renderSceneSoon), полный рендер на отпускании.
- Мёртвая зона тапа 7 px (иначе двойной тап не работает).
- backfillProject() в plan-core.js — ЕДИНАЯ точка бэкофилла настроек/проёмов,
  вызывается и из openProject, и из importJSON (не дублировать логику).
- Автоперестройка трасс: core().onChange слушает AUTOREBUILD_ON (elem-move/
  room-reshape/wall-th/wall-mat/beam-move/beam-w) в plan-routes.js и тихо
  зовёт build({silent:true}), если p.routes уже не пуст — новые хендлеры
  геометрии НЕ обязаны сами дёргать Routes.build(), это сделает подписка.
- Коннекторы (ВАГО/ГМЛ/СИЗ): pin-count распайки = ТОЧНОЕ число сходящихся
  кабелей (inCnt+outCnt по графу трасс) — точнее, чем в pool-engine.
- wallAt: у ОБЩЕЙ стены двух комнат centerline совпадает — раньше побеждала
  всегда первая комната. Теперь через wallFrame.nrm сравниваем, В СТОРОНУ
  какой комнаты физически смещён тап (side>-0.5 = "внутри"), иначе вторая
  комната необратимо недостижима для простановки точек на своей стене.
- roomNear (plan-routes.js) — фолбэк для щита/точки НЕ строго внутри полигона
  комнаты (round-off у самой стены): G.roomAt → иначе комната ближайшей стены
  через G.wallAt. Без него buildPath получал ra/rb=null и падал на кривой
  ortho()-фолбэк вместо контура/перпендикулярной проходки.
- Unfold silent-build: любой вызов EP.Plan.Routes.build() из-под развёртки
  (fullscreen тулбар и т.п.) ОБЯЗАН идти с {silent:true} — иначе build()
  зовёт sheet(), который перезаписывает innerHTML #ep-plan-sheet и стирает
  DOM самой развёртки (выглядит как самопроизвольный выход из fullscreen).
- G.blockChaseEntries(el) — визуализация штроб В БЛОК по видам (силовая:
  крайний левый пост; свет+розетка вместе: штроба между ними; свет один:
  прямо к нему; интернет/ТВ: каждый отдельно к своему посту) — ОТДЕЛЬНАЯ
  от G.blockEntryIndex/routeAnchor (та точка одна на блок и используется
  для реальной трассы, эту НЕ трогать заново без явного запроса).
- G.switchTarget(project, el, keyIdx) — куда идёт свет от клавиши выключателя:
  el.targetIds[keyIdx] (ручной выбор, targetId — legacy-алиас клавиши 0) →
  иначе ближайшая лампа/«Вывод» ТОЙ ЖЕ линии (circuitId) в той же комнате;
  без линии связь не строим. Рисуется пунктиром в plan-render.js
  (.ep-plan-swlink), цвет — по линии.
- Тип «Вывод» (output) — free:true (стена ИЛИ потолок/пол, как light/warmfloor:
  hit-стена в приоритете, иначе свободная точка), layerChoice:true — в
  редакторе точки чип «Силовой/Слаботочный» переключает el.layer.
- Выключатель: el.keys (1-3, только swKind="normal"), el.swKind (normal/pass/
  cross), el.chainNext (id следующего звена цепочки проходной/перекрёстный).
  Рендер (.ep-plan-swchain): звено с chainNext рисует провод ТОЛЬКО к
  следующему звену (не к лампе); к лампе ведёт ТОЛЬКО последнее звено
  (chainNext=null) — через switchTarget. Коннекторы (plan-calc.js
  switchTemplateKey) берут pool-engine шаблон switch_N/pass_N/cross_N по
  keys+swKind вместо всегда switch_1. ОГРАНИЧЕНИЕ (известное, не решено):
  автотрассировка (plan-routes.js build()) НЕ знает о цепочках — каждое
  звено получает свою независимую трассу к щиту, как обычная точка, а не
  только первое звено цепи. Клавишность/цепочка НЕ поддержаны у switch-постов
  ВНУТРИ блока (только у отдельно стоящего элемента switch).
- Развёртка: текст размера (.ep-plan-unfdimT) ОБЯЗАН иметь pointer-events:none
  в CSS — иначе тап точно по цифре (не рядом) находит текстовый узел (сосед
  прозрачного hit-rect'а, не потомок) через e.target, .closest() не находит
  data-pu-heightof/segof на соседе, и тап проваливается в "пустой" (ставит
  новую точку) вместо открытия карточки.
- hopVertMul(p, route) — без распайки/щита на конце хопа штроба у ЭТОЙ точки
  проходится дважды (вниз к посту и обратно вверх продолжать шлейф) — влияет
  на метраж КАБЕЛЯ (не на длину самой штробы — физическая канавка одна).
  ТП: подача обычной штробой к термостату + ВСЕГДА отдельная 50×50 от
  термостата вниз в пол (el.height). Выключатель при routeType="floor" —
  pointVert на всю высоту до потолка (линия идёт дальше к лампе), не только
  до своей точки.
- routeOff(p, circuitId) в plan-routes.js — отступ трассы от стены НЕ одно
  число на весь проект: база settings.routeOffset (QF1/без линии) + 2 см на
  каждую следующую линию по её индексу в p.circuits (QF2 +2, QF3 +4…, кап
  ×10 лэйнов), чтобы параллельные трассы разных линий вдоль одного коридора
  визуально не сливались в одну. Прокинут через contourOf/pathInRoom/
  buildPath (5-й параметр circuitId, с фолбэком на fromEl.circuitId).
  Намеренно НЕ делали отдельную логику обхода пересечений (доп. проходки
  ради одной точки налегания линий) — просил не усложнять, разный отступ
  уже снимает почти все случаи.
- Ручная однолинейка (plan-manualscheme.js): p.manualScheme.groups (УЗО/Диф)
  → lines → apps до/после УЗО. Вводной автомат/счётчик/вводное УЗО НЕ
  дублируются в manualScheme — те же p.settings.mainBreaker/meter/mainRcd,
  что и в авто-режиме (иначе два источника правды + подбор корпуса щита
  neededModules() их же считает). Линия может ссылаться на линию плана
  (line.circuitId → p.circuits) — после этого линия пропадает из «+
  линия…» у всех групп и помечается ✓ в чек-листе наверху (какие линии
  плана ещё не расставлены в схему). Реордер аппаратов/групп/линий — НЕ
  через drag в форме, а кликами по ▲▼/◀▶ прямо в SVG-превью
  (ShieldSchemeSVG.renderGost сам рисует эти кнопки у interactive:true
  дерева — data-vreorder/greorder/lreorder), форма только добавляет/
  убирает/редактирует поля. ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ (не решено, раскрыто
  пользователю): подбор корпуса щита (neededModules) считает модули ПО
  p.circuits (1 УЗО на линию), а ручная схема допускает НЕСКОЛЬКО линий
  под одним УЗО — при активном ручном режиме размер щита на плане может
  быть завышен относительно реальной сборки.
- hitAt(w, maxCm) в plan-elements.js ОБЯЗАН бить по G.elemDrawPoint (видимый
  маркер, отступ th/2+8 от стены), а НЕ по G.elemPoint (ось стены) — иначе
  тап по маркеру, если он попадает мимо мис-центрированного хит-круга,
  проваливается в hit-тест стены (G.wallAt) и открывает не то (баг: «не с
  первого клика», «задаются параметры стен»). elemDrawPoint для свободных
  элементов (light/warmfloor/output/track/junction) совпадает с elemPoint —
  фикс безопасен для них.
- isPoint (plan-routes.js) БОЛЬШЕ НЕ исключает warmfloor — раньше ТП вообще
  не участвовал в build() (ни одной трассы), хотя вся логика штроб под ТП
  (hopVertMul, сплит-штроба 25×30+50×50) уже была рассчитана НА трассу к
  ТП и просто никогда не срабатывала в авто-трассировке.
- Развёртка: тяга щита/проёма (S.drag.kind: "el"|"open"|"panel") — раньше
  drag поддерживал ТОЛЬКО p.elements (data-pu-el); щит и проёмы рисовались
  без узла-обёртки для тяги, поэтому попытка потянуть щит превращалась в
  пан всего вида, а проём вообще не двигался (тап всегда открывал
  редактор). Щит и проёмы теперь в <g data-pu-panel>/<g data-pu-open> —
  тянутся только ВДОЛЬ стены (щит сохраняет перпендикулярный отступ от
  стены через drag.perp, проём меняет offset). Persist-реплики
  "panel-move"/"opening-move" добавлены в AUTOREBUILD_ON (plan-routes.js),
  иначе построенные трассы молча устаревают после переноса щита/проёма.
- Светодиодная лента (p.ledStrips) — сегмент ВДОЛЬ КОНКРЕТНОЙ стены
  (wallId+offsetA/offsetB+height), а НЕ свободная ломаная — осознанное
  упрощение: даёт тривиальный рендер и на плане (pointAtOffset), и в
  развёртке (x=offsetA..offsetB, y=H-height, БЕЗ проекции), в отличие от
  p.beams (свободные {a,b} мировые точки, только на плане, в развёртке не
  рисуются вообще). Расстановка в plan-unfold.js: addType="led", тап-тап
  (S.ledDraft хранит первую точку до второго тапа), высота берётся с
  ПЕРВОГО тапа (лента всегда горизонтальна). Тяга — только вдоль стены
  целиком (сохраняя длину, S.drag.kind="led"), тап без тяги — confirm-
  удаление (своего редактора полей нет, только длина/позиция через тягу).
- G.switchLedTarget(project, el, keyIdx) — ОТДЕЛЬНАЯ от G.switchTarget
  функция (не трогать switchTarget — типизированный контракт возвращает
  элемент из project.elements, лента не элемент). Вызывается КАК ФОЛБЭК
  в plan-render.js, только если switchTarget вернул null (нет лампы/
  вывода той же линии) — тогда ищем ленту той же линии (circuitId) в той
  же комнате. Если в проекте есть щит с transformer:true (чекбокс в
  редакторе щита, data-pe-ptrafo) — рисуем ДВА пунктира (выключатель→щит,
  щит→середина ленты), иначе один пунктир выключатель→лента напрямую.
  ДОПУЩЕНИЕ (не уточнено пользователем, может потребовать правки): «тот
  самый» слаботочный щит ищется как `panels.find(pn => pn.transformer)` —
  ПЕРВЫЙ попавшийся щит с флагом, без учёта близости/комнаты. При
  нескольких щитах с transformer:true в одном проекте — берётся не
  обязательно ближайший.
- Тип «Вывод 24В» (output24) — НЕ привязан к ленте/трансформатору
  напрямую, обычная свободная точка (layer:"lv") для любых 24В-выводов
  общего назначения. «Вывод» (output) уже покрывает силовой вывод по
  умолчанию (layer:"power") — отдельный тип для него не заводили.
- Цены в Расчёте (plan-calc.js): priceFor(name, type) УЖЕ существовал
  (точное совпадение по имени в EP.Database, иначе двунаправленная
  подстрока), но раньше срабатывал ТОЛЬКО в toEstimate() при нажатии
  «В смету» — в самой шторке Расчёта цена не показывалась вообще. Теперь
  sheet() считает priceFor для каждой позиции сразу и показывает и
  построчно (qty×price), и общий «Итого по ценам БД» внизу; позиции без
  совпадения в БД помечены «нет цены в БД» (не 0 ₽ — чтобы не подумали,
  что материал реально бесплатный) и не входят в сумму. Логику
  сопоставления НЕ трогали (используется как есть), только вывод в UI.

## Бэклог (подтверждён пользователем)
Аудит-патч 1-5 — СДЕЛАН. Пакет клик-по-размерам/общая-стена/щит-у-стены — СДЕЛАН.
Пакет штробы-в-развёртке/выключатель→свет/тип-Вывод — СДЕЛАН.
Пакет клик-баг/многоклавишность+цепочка/×2-без-распайки/ТП-штробы/кнопка-Стена — СДЕЛАН.
Отступ трассы по линиям (QF1 15см/QF2 17см…) — СДЕЛАН.
Ручная однолинейка внутри плана (по логике общего ManualSchemeV28 + чек-лист
линий с плана) — СДЕЛАН (см. инвариант выше, включая известное ограничение
по подбору корпуса щита).
Пакет багов (клик по точке мимо, ТП без трассы, тяга щита/проёма в
развёртке) — СДЕЛАН (см. инварианты hitAt/isPoint/S.drag.kind выше).
Новые типы точек «Бра» (на стену), «Трек» (свободно, потолок) и «Вывод 24В»
(слаботочный, общего назначения) — СДЕЛАНО.
Светодиодная лента (p.ledStrips: сегмент вдоль стены, тап-тап в
развёртке, рендер на плане И в развёртке) + чекбокс «трансформатор в
щите» (маршрут выключатель→щит→лента, если найден щит с transformer:true,
иначе выключатель→лента напрямую) — СДЕЛАНО (см. инварианты выше, включая
допущение про выбор «того самого» щита — не уточнялось у пользователя).
Материалы из БД / цены ₽ прямо в Расчёте — СДЕЛАНО (priceFor уже
существовал, теперь показывается в самой шторке Расчёта + «Итого», см.
инвариант выше). Это закрывает и бэклог-пункт 4 «цены ₽ прямо в Расчёте»
— один и тот же пункт был назван по-разному в двух местах списка.

Согласованный ПОРЯДОК следующих шагов (пользователь фиксировал явно —
не менять порядок без запроса): материалы из БД — СДЕЛАНО → баланс фаз 3ф
(СЛЕДУЮЩИЙ ШАГ) → фотофиксация точек → дальше остальные крупные пункты по
мере обсуждения → смета по работам → PDF-альбом — САМЫЙ ПОСЛЕДНИЙ пункт,
даже после сметы.

Крупное, ещё не начато (порядок см. выше): 1 PDF-альбом (титул/планы по
слоям/развёртки/ведомость) — делать САМЫМ ПОСЛЕДНИМ, 2 экспорт DXF
(AutoCAD), 3 ручное редактирование трасс, 4 фотофиксация точек, 5 обход
проёмов при полу, 6 баланс фаз 3ф — СЛЕДУЮЩИЙ ШАГ, 7 шаблоны комнат,
8 автотрассировка должна учитывать цепочки проходных/перекрёстных (см.
ограничение выше), 9 смета по работам — отдельным ходом, после остального
(кроме PDF). UX-хвосты: редактор точки поверх развёртки, ГОСТ-мини-значки
в рамке постов, клавишность/цепочка для switch-постов внутри блока.
